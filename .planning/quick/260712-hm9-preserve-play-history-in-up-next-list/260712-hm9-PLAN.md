# Quick Task 260712-hm9 — Preserve play history in the Up-Next list

## Task boundary

The Up-Next list must keep **played** songs visible as playback proceeds one-by-one
(natural auto-advance), scrolling to the current song (scroll already implemented). A tap on
a song **inside** the list preserves the list; a tap on a song **outside** the list makes it
the first row and fills Up-Next with similar songs.

## CRITICAL — most of this is ALREADY IMPLEMENTED. DO NOT rebuild it.

Verified against the code + the passing test suite (189/189 green in
`src/lib/stores/player.svelte.test.ts`):

- **Played songs stay on auto-advance** — `quick-260618-lsw`. The Up-Next list slices from
  `upNextAnchorUid`'s live index, NOT the current index. Auto-advance (`next()` → `advanceTo()`
  → `play(t, {fresh:false})`) leaves the anchor put, so the just-played song stays in the slice.
  Covered by test **"Test 1 — auto-advance (next()) keeps the anchor; the played song stays in
  the slice (LSW-01)"** (`player.svelte.test.ts:4054`). ✅ no change.
- **Tap a song INSIDE the list preserves the list** — the Up-Next row `onclick` already calls
  `player.play(track, {fresh:false})` (`NowPlaying.svelte:1370`). Non-fresh = no re-anchor, no
  regenerate; only the highlight moves. ✅ no change.
- **Tap a song OUTSIDE the list → first row + similar fill** — search/home/album/related/version
  taps call `play(track, {fresh:true})`. Fresh play weaves history, sets `upNextAnchorUid =
  clicked` (so the clicked song is the first row), and `regenerate()` rebuilds the tail from
  `buildSimilarQueue` (`player.svelte.ts:2774-2796`). ✅ no change.
- **Scroll-to-current** — one-shot scroll on Up-Next open (`NowPlaying.svelte:1098`). ✅ no change.

## ROOT CAUSE of the reported "played songs discarded as soon as it ended"

`upNextAnchorUid` is set ONLY on a fresh user play / new-list install
(`player.svelte.ts` writes at lines 1838 `setQueue`, 1888 `setListQueue`, 1938 `clearQueue`,
2787 `play({fresh})`). It is **null** in the common flows that have no fresh tap:

- **Restore on mount / PWA reopen** — `restore()` (`player.svelte.ts:437`) sets `current` +
  `queue` but never sets `upNextAnchorUid`.
- It is **not persisted** — `serializePlayerState` (`player-persist.ts:74`) omits it, confirmed
  by test "keeps ONLY the 11 whitelist fields".

When the anchor is null, NowPlaying's clamp falls back to the **current** index:
`upNextStart = anchorIdx >= 0 ? anchorIdx : ci >= 0 ? ci : 0` (`NowPlaying.svelte:558`).
So a resumed session slices Up-Next from `current`, and every just-played song drops out of the
list as `current` advances — exactly the reported symptom. A user who searches-and-taps (fresh)
never hits it; a user who resumes a restored track always does.

## Fix strategy (minimal, keeps the existing anchor model + LSW-03's ci-fallback intact)

Guarantee the anchor is non-null for a resumed/restored run, and persist it so a reload keeps
the exact played-history view. NO change to NowPlaying's slice/fallback, NO change to the
fresh/non-fresh play paths, NO change to the row handlers. Keep test LSW-03 (ci-fallback for a
genuinely absent anchor) green.

<objective>
At desktop widths the app stops being a phone column in the middle of a 1440px screen: the bottom
tab bar becomes a persistent left rail, the content fills the window, and the home shelves show
many more tiles per row with a pointer-friendly sideways scroll affordance.

Purpose: backlog phase 999.4's last open item. The user chose the fullest option (rail + full-width
content + wide multi-column shelves, YouTube Music desktop style).
Output: one new breakpoint, one new CSS token, one small component, two tests. Mobile byte-for-byte
unchanged in behaviour.
</objective>

<decisions>

Recorded here because the user asked for autonomous progress with the obvious option taken.

**D-1 - The breakpoint is `min-width: 1024px`, and it is the app's second and last one.**
The app today has exactly ONE width breakpoint: `@media (min-width: 640px)`, used twice
(`CompactPager.svelte:68`, `+page.svelte:1047`) to stop a 90vw column sprawling. 640 / 768 / 1024
is the standard sm/md/lg scale that 640 already belongs to, so `lg = 1024px` is the next rung of
the scale already in the file - not a new scale. 640px itself is far too low for a rail (landscape
phones are 844-932px wide and must keep the bottom bar). Consequence: iPad portrait (820px) keeps
the mobile layout; iPad landscape (1024px) gets the rail. Accepted.

**D-2 - The rail is the SAME `<nav class="tabbar">` element, restyled by media query.**
No second nav component, no shared nav-config module, no `matchMedia` in JS. The `tabs` array in
`+layout.svelte:175` stays the only definition. A second navigation source of truth is a defect
(explicit constraint); the laziest way to guarantee there isn't one is to not create a second DOM
node. This also makes keyboard + screen-reader parity structural rather than something to test:
it is literally the same `<nav>` with the same `<a>` children, so it is already tab-reachable and
already announced as a navigation landmark.

**D-3 - Rail shape: 88px wide, icon above label, exactly the three existing tabs.**
Nothing beyond primary navigation. No playlist list, no upgrade entry, no header. This is
YouTube Music's mini-guide, and it is a pure restyle of `.tab` (which is already a centred
icon-over-label column) instead of a new row layout. Prefer the smaller thing.

**D-4 - No `aria-label` on the `<nav>`, no new i18n keys for the rail.**
There is one `<nav>` landmark in the whole app and it is already announced as "navigation". Naming
it would cost 15 dictionary edits while another agent has those files open, for near-zero screen
reader gain. We DO add `aria-current="page"` to the active tab - one attribute, no strings, no
visual change, and it improves the announcement on mobile too.

**D-5 - Content max-width at desktop is 1920px, not unlimited.**
`.content` is pinned at `max-width: 720px` today. At >=1024 it becomes `max-width: 1920px` with
24px side padding. Every laptop (1440/1512/1728) therefore fills edge to edge - the user's ask -
while a 3440px ultrawide does not stretch a CompactRow to 3400px, which reads as broken rather
than generous. `ponytail:` hard cap, revisit if someone actually runs this on an ultrawide.

**D-6 - The Nowbar becomes the persistent desktop player bar. NowPlaying is NOT redesigned.**
The Nowbar is `position: fixed; bottom: var(--tabbar-h)`. At desktop the tab bar is no longer at
the bottom, so the Nowbar moves to `bottom: 0; left: var(--rail-w)` - it spans from the rail to
the right edge. That is exactly YouTube Music's desktop model and it costs three CSS lines.
**Explicitly NOT doing:** a desktop two-pane now-playing (cover left, queue + lyrics right), a
desktop-specific transport layout, or any restructuring of `NowPlaying.svelte`. Tapping the
Nowbar at desktop still opens the same full-screen sheet, which still covers the rail. CLAUDE.md
flags `NowPlaying.svelte` (~2000 lines) as a re-render hotspot that should be SPLIT, not grown;
growing it with a desktop variant inside a quick task is how that file got to 2000 lines.

**D-7 - The search entry does not change at desktop.**
`/search` stays a rail destination with its own in-page input. No persistent header search field:
that is a new always-mounted surface with its own state, focus management, and strings, and it
duplicates the search page's input. Nav parity with the tab bar, nothing invented.

**D-8 - Desktop shelf density: tiles keep their size, the COUNT grows with the window.**
- `.albumrow` (the main shelf): needs nothing. Tiles are a fixed `130px` flex basis, so a
  1900px-wide container shows ~13 instead of ~5 for free. Verify, do not touch.
- `.grid` (the fallback grid) is `repeat(var(--home-grid-cols, 3), 1fr)`; at 1900px that is three
  600px tiles. At desktop it becomes `repeat(auto-fill, minmax(150px, 1fr))` - the user's chosen
  column count stays authoritative on mobile, and desktop derives the count from the width. This
  deliberately overrides a user setting at desktop widths; the alternative (`calc()` inside
  `repeat()`) is not valid CSS.
- `HomeGridPager`'s `.page` is a 3x3 snap page with a dot indicator and `TILES_PER_PAGE = 9` in
  JS. At desktop the columns are capped (`repeat(3, minmax(0, 220px))`, `justify-content: start`)
  so the 3x3 structure survives instead of sprawling. A desktop-specific pagination (more tiles
  per page) is out of scope.
- `CompactPager` already caps its column at 420px above 640px; at 1900px that yields ~4 columns
  side by side. Correct as-is.

**D-9 - Reduced motion.** The rail swap is a media-query restyle with no animation, so there is
nothing to gate. `prefers-reduced-motion` IS honoured in the chevron scroll (`behavior: 'smooth'`
-> `'auto'`).

**D-10 - No i18n additions at all.** The chevron buttons reuse the existing `nowplaying.previous`
/ `nowplaying.next` keys ("Previous" / "Next" in every dictionary). Zero dictionary edits, zero
collision with the agent currently editing `src/lib/i18n/*.ts`. Tradeoff: those labels are player
transport wording, so several buttons on a page share the name "Next". Upgrade path is dedicated
`shelf.scrollPrev` / `shelf.scrollNext` keys once the i18n files are free.

**Off-limits, by instruction:** `src/routes/(app)/settings/**`, `src/lib/stores/settings.svelte.ts`,
`src/lib/services/{retag,blob-store,audio-tags}.ts`, `android/**`, `src/lib/i18n/*.ts`. This plan
touches none of them. Known cosmetic consequence: `settings/data` and `settings/downloads` each
have a `.flash` toast at `bottom: calc(var(--tabbar-h) + 70px)`, which at desktop will float 56px
higher than it needs to. Left alone on purpose - it is a toast offset, not a defect, and those
files belong to another agent right now.

</decisions>

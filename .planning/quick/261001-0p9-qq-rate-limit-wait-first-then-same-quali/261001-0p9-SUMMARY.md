# Quick 261001-0p9: qq rate limit, wait first, then a same-quality donor

When qq rate-limits a song during an album download, the album now retries qq first (3, 6, 9 and 12 s, 30 s in total). Only if qq is still limited after that does it look at other sources. It takes a donor with the same quality and format as the download tier first ("qq FLAC → another source's FLAC, not an mp3"). If none matches, it takes the best-ranked other non-ytmusic donor so the album still finishes.

## What changed

- `download-track.ts`: two new pure exports. `donorRank` gives 3 for lossless, 2 for 320, 1 for 128 and 0 for unknown, and the container wins over the tag. `donorMatchesTier` requires the same band AND the same format class; an unknown container is judged on band alone. `downloadFromDonor` now takes `prefer?: 'tier'` instead of `requireTier`. It is still a single walk: a matching donor is tried as soon as it is seen, the others are collected, and if nothing matched and saved they are tried by rank, highest first (stable sort). Calls with no options behave as before.
- `download-album.ts`: `RETRY_BACKOFF_MS = [3000, 6000, 9000, 12000]`. The backoff loop comes first, then a single `downloadFromDonor(tr, dl, { exclude: [tr.source], prefer: 'tier' })` for 'rate-limited' or 'no-audio'. The header has a new paragraph explaining this, and the `ponytail:` line now reads "4 retries / 30 s cap, one donor walk".

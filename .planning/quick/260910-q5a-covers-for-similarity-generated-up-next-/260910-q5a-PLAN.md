usable per-track image in practice (live probe: 20 pairs, `withImage: 0`), so the Gap 3 (26-07) seed is
dead, and (b) the Up Next tile reads ONLY `resolvedCovers[uid] ?? track.cover` — it is not bound to the
shared reactive cover cache, so nothing that lands later can ever repaint it.

Fix both, surgically, with zero new resolvers and zero player-store edits:
1. Bind the tile to the shared cache (`readCoverByUidOrName` + `coverVersion()`), keeping `track.cover`
   ahead of the cache so quick-260910-piz album rows keep winning.
2. Fill covers post-paint with the EXISTING sanctioned `backfillCovers` (Deezer → iTunes → CN, CAP=6 pool,
   skip-cached, 5-min negative-miss memo) from ONE gated component `$effect` (sheet open + Up Next tab),
   explicit `max: 20`, aborted on re-run.

Purpose: the user sees album art on generated Up Next rows; the network cost is a stated, bounded number;
the three documented flood classes (`api-fetch-flood-freeze`, `nowbar-freeze-reresolve-loop`,
`restore-effect-self-invalidation-loop`) are structurally avoided.
Output: `src/lib/services/upnext-covers.ts` (+ node test), a two-site edit to `NowPlaying.svelte`.

Coverage achieved (state plainly — do not overclaim):
- Rows already in the shared cache (played before, seen on Home, a carousel neighbour): art IMMEDIATELY on open.
- Rows Deezer can name-match (most Western catalogue): art lands within ~1-3 s of opening the Up Next tab.
- Rows only iTunes/CN can match (much CN catalogue): art lands later (deep tiers fire only on a Deezer miss).
- Rows no tier can match: stay gradients; retried after the 5-min miss memo or on page reload.
- While the Up Next tab is NOT open, nothing is fetched — first open pays the fill.

  and edge-cached anyway.

  install path (regenerate, ensureAhead, diverse safety-net, restore) in one site.

## D-1 — THE REWRITE TRIGGER: explicit gesture = eager; everything automatic = lazy or never

| Event | Writes the file? | Why |
|---|---|---|
| User taps a cover in the cover picker (`pickCover`) | **YES, immediately** — one file, one wasm pass | An explicit, deliberate, one-at-a-time gesture on one song. Identical in cost and shape to the metadata-editor Save that already ships. |
| User taps an LRC in the lyrics picker (`pickLyrics`) | **YES, immediately** | Same. |
| A network lyric backfill SUCCEEDS for a song with a local copy | **YES, once per uid per session, off the critical path** | Self-terminating: once the LRC is in the file, `localEnrichment` finds it on the next play and `backfillLyrics` never runs for that uid again. This is the ONLY automatic writer, and it can only fire for a file that currently has no usable embedded LRC. |
| An automatic cover resolve / backfill / `healCover` / `adoptCover` | **NEVER** | This is the thrash case. `healCover` alone can fire per render on a flaky image; rewriting a 27 MB FLAC's tags there would be a disaster. The pin already makes the user's choice permanent in the app WITHOUT touching the file. |
| The Settings -> Downloads sweep | **YES — it already does**, and now carries the pinned cover + pinned LRC | The opt-in, confirmed, progress-reported batch. This is the repair path for every file pinned or downloaded before this task. |

**Why it cannot thrash a large file:** the only automatic writer is gated on a network lyric
success for a file that lacks embedded lyrics, capped at one attempt per uid per session by a
player-owned Set, serialized app-wide through `syncFileTags`, and refused outright by
`tagAudioBlob`'s `TAG_MAX_BYTES` (40 MB) ceiling. Every other writer needs a finger on the screen.

## D-2 — `getPinnedCover` IS the remember-mechanism. Do not add a second one.

Verified at every read site before planning, all of which already lead with the pin:
`cover-version.svelte.ts:99` (`readCoverByUidOrName`), `:113` (`readPinnedCover`, the leading rung
of `pickRowCover` on every list surface), `player.svelte.ts:580` + `:3213` (the play/restore cover
seed), `:3226` + `:3626` + `:794` (a resolver, an adopt and a local file's own embedded art all
YIELD to a pin), `:3935` (`healCover` unpins ONLY a URL that genuinely failed to load).
A second "override" store would be a bug factory. The pin persists in its own localStorage key with
no TTL and no LRU.

## D-3 — the web build's ceiling, stated not worked around

On web, `blobStore.put` rewrites the IndexedDB record — the copy the app serves offline — so
in-app playback picks up new art/lyrics immediately. The copy in the user's Downloads folder came
from an `<a download>` click and **no browser API can reach back into it**; it keeps its old tags
until the song is re-downloaded. This is `quick-260919-1eh`'s documented platform ceiling. Do not
attempt a workaround. On native both copies are rewritten (app-private + the 36-D-19 replacing
public `Music/OpenMusic/` save).

## D-4 — F2's numbers come from the LOCAL BYTES, never a source probe

A song that is already downloaded has an authoritative answer on the device. `probeDownload`
(network, resolve + HEAD) answers "what WOULD I get"; the new `localFileMeta` answers "what DO I
have". Size is `blob.size` / `content-length`; the container is sniffed from the file's first 12
bytes, never from `blob.type` (the qq CDN lies in Content-Type — `download-filename.ts`) and never
from a URL extension. Quality rides the persisted `Track.qualityLabel`, and `formatDownloadMeta`
already drops it for a lossless container, which is exactly right.

## D-5 — an offline play fires NO lyric walk

`backfillLyrics` currently walks up to ~5 sources when the file carried no usable LRC. Offline that
walk cannot succeed and the pane shows nothing anyway. Gate it on `navigator.onLine` and let the
existing `nowplaying.noLyrics` ("No lyrics for this track.") be the honest degrade — no new string.

## D-6 — a user-typed file name becomes sticky (the enabling fix for D-1)

Today `retagOne` ALWAYS recomputes the on-disk name from title+artist when the caller supplies no
`filename`. So the moment F1/F3 add new rewrite triggers, a cover pin would silently rename a file
the user deliberately named hours ago via `quick-260919-30x`'s File name field. The shipped Settings
sweep has the same hole. Fix it once, inside `retagOne`: remember a name the user TYPED, reuse it
when no caller supplies one. A DERIVED name is deliberately not remembered, so editing the title
still renames the file exactly as it does today.

## D-7 — the pin paths pass the library's title/artist/album, like the sweep does

Checked, not assumed: `library.applyMetadata` (`library.svelte.ts:164-182`) PERSISTS an editor edit
into `library.downloads`, `liked` and every playlist. So `names.dnTitle(track.title)` reproduces the
user's own edit, not the catalog string — a cover pin cannot clobber a manual metadata edit. The
entry construction is a verbatim copy of the Settings sweep's
(`settings/downloads/+page.svelte:140-143`): `dnTitle` / `dnArtist` / `names.zhLock(album)`.

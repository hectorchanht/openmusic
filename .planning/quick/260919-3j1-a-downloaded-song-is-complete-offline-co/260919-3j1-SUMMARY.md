## What writes a file's tags, and what deliberately does not

`syncFileTags` is now the only door to `retagOne`, and `retagOne` is the only door to
`blobStore.put` for a tag rewrite. Every call site in `src/` (excluding tests), enumerated:

```

src/lib/components/TrackMenu.svelte:316:    void syncFileTags(entry)     <- inside writeTagsForGesture
src/lib/components/MetadataEditor.svelte:123: await syncFileTags({       <- inside save()

```

### Triggers that DO write a file

| Trigger | Entry point | Bound |
|---|---|---|
| Metadata editor **Save** | `MetadataEditor.save()` → `syncFileTags` | explicit tap; `saving` guard; one file |

### How I verified `healCover` cannot reach a rewrite — traced, not asserted

1. `grep -rn 'syncFileTags(' src/` (non-test) returns exactly the three sites above. There is no
   fourth writer, so reaching a rewrite means reaching one of those three.
2. `player.svelte.ts:828` sits inside `embedLyricsIntoFile`. Its only two callers are
   `player.svelte.ts:760` and `:773` — the two **lyric** success branches of `backfillLyrics`.
   Neither is a cover path, and nothing in the cover chain calls `backfillLyrics`.
3. `TrackMenu.svelte:316` sits inside `writeTagsForGesture`. Its only two callers are
   `TrackMenu.svelte:258` (`pickCover`) and `:361` (`pickLyrics`) — both bodies of a tap handler on
   a picker row, reachable only from a user tap. `healCover` lives in the player store and has no
   reference to the component.
4. `MetadataEditor.svelte:123` is inside `save()`, a button `onclick`.
5. `healCover`'s own body calls exactly four things: `this.probeCover`, `unpinCover`,
   `removeCoverBoth`, `resolveCoverForTrack`. The modules those live in —
   `cover-backfill.ts`, `cover-version.svelte.ts`, `cover-cache.ts` — contain **no** occurrence of
   `retagOne` or `syncFileTags` (Task 8 grep 3, empty). `adoptCover` likewise reaches only
   `writeCoverBoth` (a localStorage cache write), `runFallback` and `clearMedia`.

So the thrash case the plan was built to avoid — `healCover` firing per render on a flaky image and
rewriting a 27 MB FLAC each time — has no path to a file write at all. A cover reaches a file only
when a finger taps a candidate tile, or when the user runs the opt-in sweep.

### Why the one automatic writer cannot thrash

`embedLyricsIntoFile` is gated five ways, and the first two are the load-bearing pair:

1. It can only fire for a file whose **own tags carried no usable LRC** — `enrichFromLocalFile`
   gates `backfillLyrics` on exactly that (37-D-07).
2. It is **self-terminating**: once the LRC is in the file, the next play's `localEnrichment` finds
   it, `backfillLyrics` is never called for that uid again, and neither is this.
3. One attempt per uid per session even on failure — the uid joins the plain `lyricEmbedTried` Set
   **before** the await.
4. Serialized app-wide by `syncFileTags`, so it can never run beside an editor save or a pin.
5. `tagAudioBlob` refuses anything over `TAG_MAX_BYTES` (40 MB) with `'skipped-size'`, leaving the
   file byte-identical.

## Does a song downloaded BEFORE today ever become lyrics-self-sufficient?

**Yes, by two routes, and one of them is automatic.**

1. **The automatic embed (no user action).** Play the song online. Its file carries no usable LRC,
   so `enrichFromLocalFile` calls `backfillLyrics`, the network walk succeeds, the patch lands on
   `current.lrc`, and `embedLyricsIntoFile` writes that LRC into the file. From the **next** play
   on, `localEnrichment` reads it off the file and no network is involved. This needs one online
   play per song and nothing else.
2. **The Settings → Downloads sweep** repairs the batch in one opt-in pass, carrying both the pinned
   cover and the pinned LRC.
3. Pinning an LRC from the track menu also writes it immediately.

The only songs that stay lyrics-dependent are those the lyric walk never finds words for — which is
the honest outcome, not a gap.

## The shipped Settings-sweep bug the planner found

**Confirmed present, and fixed.** `settings/downloads/+page.svelte`'s `onMount` entry loop built
`cover: d.cover` — the **persisted** `Track.cover`. That is neither the user's pin (`PIN_KEY`, read
first by every other cover surface in the app) nor the shared reactive cache every list row renders
from. So the batch retag had always written stale art into files, and a cover pin was invisible to
it entirely.

It now reads the same ladder `download-track.ts` uses, minus `player.resolvedCover` (a now-playing
concept with no place in a batch loop):

```ts
cover: readPinnedCover(d.uid) ?? readCoverByUidOrName(d.uid, d.artist, d.title) ?? d.cover
```

with RAW `d.artist` / `d.title` for the cache lookup, not `dnArtist`/`dnTitle` — the name layer is
`matchKey`'d on raw catalog metadata, so a display-language string would miss the cache for exactly
the users the script conversion exists for.

Together with the pinned-LRC line added beside it, **the sweep is now a genuine repair path for
everything downloaded or pinned before today**: pinned cover, pinned lyrics, script-locked album
(2jo), and — via Task 1 — without clobbering a user-typed file name.

## Where the size / format / quality numbers come from

- **Size** — `blob.size` on web (the IndexedDB `get` hands back a *lazy* Blob handle, so reading
  `.size` costs nothing), `content-length` on native.
- **Container** — `containerFromMagic`, sniffed from the file's first 12 bytes: `fLaC`, `OggS`,
  `RIFF`+`WAVE`, `ftyp` at offset 4, `ID3`, and a bare `0xFF 0xE0`-masked MPEG frame sync. Never
  `blob.type` (the qq CDN lies in Content-Type) and never a URL extension. Unknown returns `null`
  and the label degrades to size-only — the module's NEVER GUESS A CONTAINER rule.
- **Quality** — the persisted `Track.qualityLabel`, and `formatDownloadMeta` already drops it for a
  lossless container, so a FLAC reads `FLAC · 27.9 MB` rather than `LOSSLESS · FLAC · 27.9 MB`.

**No network probe, ever, for an already-downloaded song**, and this is enforced rather than
intended:

- The two probe effects in `TrackMenu` are **mutually exclusive by gate**: `dlProbe` fires only on
  `blobPresent === false`, `localProbe` only on `blobPresent === true`. Neither can run for the same
  song, so a downloaded song never pays a resolve or a HEAD.
- `blobStore.stat` reads **12 bytes**, never the file. The web test spies on the Blob and asserts
  `blob.arrayBuffer()` is not called and `blob.slice(0, 12)` is; the native test asserts the stream
  is cancelled and `res.blob()` / `res.arrayBuffer()` are never touched.
- The `localFileMeta` suite installs a `fetch` that **throws if called**, then asserts the happy
  path still produces `FLAC · 27.9 MB`.
- Results are memoised per uid under a distinct `local|` key prefix; the download *tier* is
  deliberately not part of that key, because the file on disk does not change when the setting does.

## Deviations from Plan

### [Rule 1 — Bug] `navigator.onLine` gate uses the house `=== false` idiom, not `!navigator.onLine`

- **Found during:** Task 6.
- **Issue:** the plan specified `browser && !navigator.onLine`. Node 22's global `navigator` exists
  but has **no** `onLine` property (`'onLine' in navigator === false`), so `!navigator.onLine`
  evaluates `!undefined === true` — the gate would have read "offline" in the entire test
  environment and silently disabled every existing lyric-backfill test (the 31-D-08 cache-hit suite
  and the 37-D-01 ordinary-download case), which would have gone green for the wrong reason.
- **Fix:** used `typeof navigator !== 'undefined' && navigator.onLine === false`, which is the
  verbatim idiom `runFallback`'s own D-08 offline gate already uses 3,600 lines down the same file.
  Identical behaviour in a browser; an environment lacking the property reads as ONLINE, never
  offline. Pinned by a test (`'an environment with no navigator.onLine property reads as ONLINE'`).
- **Files:** `src/lib/stores/player.svelte.ts`, `src/lib/stores/player.svelte.test.ts`
- **Commit:** `341ebca`

## Assumption Drift (advisory)

**The Settings sweep's `d.lrc` fallback is almost always `null`.**

- **Planned:** Task 7(b) specifies `lyrics: getPinnedLyrics(d.uid) ?? d.lrc ?? undefined`.
- **Actual:** `player-persist.ts` explicitly NULLs `lrc` / `lrcUrl` / `audioUrl` before persisting
  (`lrc: null` at line 111), and `library.downloads` is restored from that persisted shape. So
  `d.lrc` is null for every row that survived a reload — the **pin is the only real carrier** in
  that expression, and `?? d.lrc` only ever contributes within a single live session.
- **Why it matters:** the line is correct and harmless (the `?? undefined` omission keeps the
  file's own lyrics either way), but a reader could conclude the sweep carries the app's known
  lyrics generally. It does not. The automatic embed is what gets lyrics into files at scale; the
  sweep carries *pins*.
- Recorded as written, per the plan. Not a deviation.

## Threat Flags

None. No new network endpoint, no new auth path, no new remote host. `containerFromMagic` reads
untrusted bytes but only compares them against fixed constants (T-3j1-05, `accept`); they are never
rendered, executed, or used to build a path. The two new trust boundaries the plan identified are
both mitigated as specified:

- **T-3j1-01** — the recorded filename fallback sits **inside** the existing `sanitizeFilename(...)`
  call in `retagOne`, so a hand-edited `../evil` is re-sanitized on read; the extension is still
  `out.format`, the sniffed container. Pinned by two tests.
- **T-3j1-02** — `setStoredName` no-ops on an empty uid/base and slices to `MAX_FILENAME_BASE`;
  `del(uid)` clears the key **above** the platform fork, so a device uid's early return cannot skip
  it and an entry cannot outlive its file. Recorded only on a `'tagged'` outcome with a
  caller-supplied name. Pinned by five tests.
- **T-3j1-04** — nothing in this plan writes, renames, moves or deletes a `device:` file.
  `retagOne`'s `if (isDeviceUid(entry.uid)) return 'device-skipped'` is still its first statement;
  `writeTagsForGesture` and `embedLyricsIntoFile` each add a second, independent refusal;
  `blobStore.stat` only READS (through the same content-URI path `nativeGet` uses), which is why the
  Detail sheet's File row works for an imported song while nothing may write to it.

## Could NOT be verified without a device or a live browser

These are unverified. I am not claiming them.

1. The Downloaded row actually rendering `Downloaded   FLAC · 27.9 MB` on a real long-press —
   `blobStore.stat`'s **native** branch was tested only against a mocked Capacitor local server, so
   the real `content-length` + `body.getReader()` behaviour of `WebViewLocalServer` on an Android
   content URI is untested. If the local server omits `content-length` for a content URI, the row
   will show nothing rather than a wrong number (`stat` returns null on a non-finite size) — a
   graceful degrade, but a degrade.
2. The Detail sheet's `File` row on an imported `device:` song, which is the one path that reads a
   MediaStore content URI in place.
3. That a cover pin's new art is visible in the phone's own music app afterwards (the MediaStore
   replacing-save is 36-D-19 plumbing this plan reuses but does not change).
4. **The D-6 regression case itself:** rename a downloaded file in the editor, then change its
   cover, and confirm the file keeps the user's name. The logic is unit-pinned in `retag.test.ts`,
   but the localStorage round-trip on a real device is not.
5. Lyrics appearing online, then still appearing in airplane mode on a replay (the embed's whole
   point), and `No lyrics for this track.` appearing promptly with no spinner when offline.
6. Whether the one wasm tag pass the automatic embed runs mid-playback is audible on a large FLAC.
   The blob `<audio>` reads from is already materialised before it starts, so it cannot break the
   play — but a hiccup is a device-only observation. The upgrade path is recorded in a `ponytail:`
   comment: move the call to the `ended` handler, do not add a timer.
7. The web build's documented ceiling is **unchanged and not worked around** (D-3): `blobStore.put`
   rewrites the IndexedDB record, so in-app playback picks up new art and lyrics immediately, but
   the copy in the browser's Downloads folder came from an `<a download>` click and no browser API
   can reach back into it. It keeps its old tags until re-downloaded.

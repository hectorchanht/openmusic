<objective>
Fix the share card showing the branded OpenMusic fallback instead of album art for most songs.

**Root cause (verified, do not re-investigate):** `quick-260919-0mw` put YouTube Music at the front of `resolveTrackChain` (cover-backfill.ts L171-190), so `activeCover` in TrackMenu is now usually a `lh3.googleusercontent.com` / `i.ytimg.com` URL. `coverToken()` (share.ts L331) is a CLOSED grammar — `d:` Deezer, `l:` Last.fm, `k:` kuwo, `i:` iTunes-by-numeric-id — and returns null for those hosts. `songShareUrl()` (L427-428) then emits no `?ci=` at all, `/api/og` re-resolves from text, and on a miss serves `OG_FALLBACK_BYTES`. The carrier grammar was never revisited when the tier order changed.

**Fix (user-named: ytmusic → iTunes):** when the displayed cover cannot be tokenized, PREWARM the iTunes cover for the same song while the menu is open, and have `doShare()` carry that instead. `itunesSongCover → fetchTopArtwork → rememberItunesId` retains the numeric id in the same response (itunes-cover.ts L178), so `recallItunesId(mzstaticUrl)` yields the id and `coverToken` emits `i:<id>`.

**Rejected alternative (record, do not choose):** adding googleusercontent/ytimg to the token grammar + og-cover's host allow-list. A googleusercontent artwork URL is an opaque irregular path with `=w120-h120-s-l90-rj` suffixes — nothing structural to close a grammar over (the same reason iTunes is carried by ID, not path — see the coverToken doc comment, share.ts L324-329). It would also WIDEN the set of hosts `/api/og` fetches, which T-3uo-02 forbids.

**Why the lookup is a prewarm and not an await in doShare:** `navigator.share()` must run synchronously inside the user gesture on iOS Safari. The existing doShare comment block (L750-760) already documents that both display strings are computed synchronously for exactly this reason. An `await itunesSongCover()` before `nav.share()` would break sharing on iOS.

**Open questions — answered from the code:**
1. *Does the iTunes id survive long enough?* Yes. `rememberItunesId` writes the `itunes:<artworkKey>` family into the shared cover cache (cover-cache.ts L121-146): 14-day TTL, 2000-entry write-time LRU, cleared by the same clear button. A repeat share still re-issues one iTunes GET per menu open unless memoised — so the effect memoises the mzstatic URL per `track.uid` in a module-scope `Map` for the session (hits only; a miss/abort is NOT memoised so a transient failure never sticks — matches the never-cache-a-failure convention in CLAUDE.md). The id then comes from the cache, not from the network.
2. *Should the prewarm write the iTunes cover into the shared cover cache (`writeCoverBoth`)?* **NO.** The user asked about the SHARE CARD only. `activeCover` reads `readCoverByUidOrName`, `player.resolvedCover` and `track.cover` — writing the iTunes URL under the uid/name key would flip the displayed art from the YTM cover to the iTunes cover on every list row and the hero. The fallback lives in component `$state` + a module memo, never in the cover cache.
3. *Is `activeCover` available at menu-open time?* Yes — it is a synchronous `$derived` (TrackMenu L162-170) over the pin store, `player.resolvedCover`, the shared cache and the stub's `cover`. The effect can decide on the first run; if `activeCover` later changes (e.g. the hero resolves), the effect re-runs and re-decides.
4. *Do album/artist share links share the gap?* No. `entityCardUrl` (share.ts L484-488) is carrier-free by design — it never emitted `?ci=`, so those cards have always relied on server-side text re-resolution. Not a regression from 0mw; **scoped out** of this task. If album/artist cards also show the branded fallback too often, that is a separate follow-up ("carry a cover id on entity cards").

Purpose: share links unfurl with real album art again on the YTM-first tier chain.
Output: TrackMenu prewarm + synchronous pick in doShare; one grammar-pin test.

<objective>
Relax the SvelteKit player-store prefetch so endless playback survives without tripping audio-source bot detection. Today prefetch fires the INSTANT playback starts (`play()` → `primeNext()` → `prefetchNext()`) and `prefetchNext()` is a bounded FORWARD-RESOLVE loop that walks up to `PREFETCH_MAX_CANDIDATES = 4` queue entries until one resolves — so a single play can fire several proxy resolves back-to-back at t=0. Combined with auto-advance, >5 songs in a short window read as a bot burst and get blocked.

Change to a slow, single-song lookahead:
1. Prefetch ONLY the immediate-next track (one resolve, source-specific via the existing `ensureTrackDetails`). Drop the multi-candidate forward-resolve walk.
2. Trigger prefetch only AFTER the current song has been actually playing for ~5s (hung off the existing `timeupdate` listener), NOT on play entry.
3. If the user skips before the 5s trigger fires, no prefetch ran — the next song resolves on-demand inside the next `play()`. No error spam.
4. Keep failure/skip handling relaxed (the loop-guard is already commented out; do not re-enable it).

Purpose: maximize per-source hit success and give end-to-end listeners an endless, gapless-enough experience without bot-blocking.
Output: edited `player.svelte.ts` + updated/added tests, full suite green.
</objective>

Confirmed by reading player.svelte.ts + player.svelte.test.ts + catalog.ts + fallback.ts:

- TRIGGER (too eager): `prefetchNext()` is only ever fired via `primeNext()` (player.svelte.ts:1259-1262, `await ensureAhead()` then `await prefetchNext()`). `primeNext()` is called from `play()` at EVERY entry: offline-blob path (1415), fresh+generated (1510, after regenerate), fresh+same-list (1512), and non-fresh auto-advance/failover (1515). So prefetch fires the moment a track is set, before any playback — the burst trigger.

- MULTI-SONG LOOKAHEAD (too aggressive): `prefetchNext()` (1139-1216) is a BOUNDED FORWARD-RESOLVE loop over indices `firstIndex .. min(i+PREFETCH_MAX_CANDIDATES, len-1)` (`PREFETCH_MAX_CANDIDATES = 4`, declared line 137). It `await ensureTrackDetails(target, sig)` per candidate, skipping rejects / no-audioUrl, until it LANDS one playable track. So a stretch of failing sources fires up to 4 resolves in one invocation — multiplied by the t=0 trigger = burst.

- PER-PREFETCH FAN-OUT: NONE inside the prefetch path. `prefetchNext` resolves ONE already-source-specific queue entry via `ensureTrackDetails` (single track, single source). Cross-source fan-out lives in `searchAll` (catalog.ts) used by `regenerate`/`runFallback`/`buildSimilarQueue`, already staggered (`SEARCH_STAGGER_MS = 200`). So the fix is at the prefetch trigger + candidate-count, NOT the resolve internals.

- FAILURE/SKIP handling: `runFallback` (1666) → `handleTotalFailure` (1748). The loop-guard cap (`tripLoopGuard`) is ALREADY commented out (913-925, 1759-1762, 1775-1786) — `consecutiveFailures` is still incremented but never trips a STOP. `handleTotalFailure` emits a batched skip notice + `next()`. These do not need to be torn out for this task — keep them as-is (relaxed already); just do NOT re-enable the commented loop-guard.

- PLAYBACK-TIME TIMER: the `timeupdate` listener (798-818) fires ~4×/sec while audio plays and already maintains `this.currentTime`. This is the hook for the "~5s of playback" gate.

- CACHING / no double-fetch: `prefetchNext` writes the resolved track back into `queue[writeIdx]` (1201) and warms `preloadedAudio`/`preloadedCover`. The later `play()` calls idempotent `ensureTrackDetails` (no-op for a `detailsLoaded` track) → instant start. Preserve this write-back-into-queue contract for the single immediate-next track.

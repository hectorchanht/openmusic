<objective>
Add a metadata editor popup for a song the app holds an offline copy of: edit song title, artist and
album, write them into the audio file's OWN tags together with the cover and lyrics the app currently
shows, and repaint every surface that displays the song.

Purpose: a downloaded file must be self-describing offline. Phase 36 taught the app to WRITE tags at
download time and Phase 37 taught it to READ them back; the one missing verb is EDIT.

Output: one new sheet component, one exported single-file save path (reusing the Phase 36 codec
verbatim), two store seams, and the i18n keys for all 15 dictionaries.
</objective>

<scope_decisions>
Recorded, not asked (the developer said take the obvious option).

**D-1 — TAGS ONLY. No file rename.** "Let the user rename the downloaded file" is backlog 999.2 and is
NOT this task. Caveat worth knowing, and NOT a new behaviour: on native, `blobStore.put`'s third
argument is the human filename derived from artist+title, and 36-D-19 makes a re-put replace the
previous public `Music/OpenMusic/` entry. So editing the artist or title DOES rename the public copy as
a side effect — that is existing retag behaviour and it is the right one (a file called
`Unknown - track01.m4a` sitting next to a tag that says otherwise is the bug being fixed). The
app-private copy stays uid-keyed. 999.2 (an arbitrary user-chosen filename) stays out of scope.

**D-2 — App-owned downloads ONLY. `device:` tracks are EXCLUDED, deliberately.** The brief asked for
imported device tracks too. They cannot be done cleanly and they are a data-loss hazard:

- `blobStore.nativeGet` / `nativeHas` short-circuit a `device:` uid to the MediaStore **content URI**
  and read the user's file IN PLACE (34-D-05). `nativePut` has no such short-circuit — it would write
  an orphan app-private copy that `get` will never read, then `MediaStoreSaver.saveToMusic` a SECOND
  public copy of a song the user already has. Net result: a silent duplicate of the user's own music
  and an edit that never shows up.
- 34 Pitfall 1 ("an imported file is the USER'S file, not the app's") already forbids this module
  mutating a device file.

Upgrade path when someone wants it: a Kotlin `openFileDescriptor(uri, "rw")` in-place rewrite plus a
MediaStore column update — a native change with its own device UAT, not a quick task.

**Root cause, fixed here:** the SHIPPED Settings -> Downloads batch retag already has this bug. Its
`eligible` list is `library.downloads` filtered by `blobStore.has`, imported rows live in
`library.downloads`, and `has` returns true for them — so the sweep was already feeding device uids to
`blobStore.put`. The guard therefore goes INSIDE `retagOne` (Task 1), where the batch sweep and the new
editor both pass through it. One guard, both callers, zero call-site cost.

**D-3 — BOTH builds ship; one honest gap.** The save writes through `blobStore.put`, which already owns
the bytes on both platforms: web rewrites the IndexedDB record (what the app serves offline); native
rewrites the app-private copy AND replaces the public `Music/OpenMusic/` copy, so the phone's own music
app shows the edit. **Gap:** on the web build, the copy the user saved to their Downloads folder via the
original `<a download>` click is unreachable by any browser API and stays untagged. Re-download to
refresh it. No web API can close this; do not attempt one.

**D-4 — An empty field leaves that tag UNCHANGED.** `writeAudioTags` only calls a setter for a truthy
field, so omission preserves what is in the file. Field CLEARING is not supported (it would need a
delete verb in the codec). Empty input therefore means "don't touch", never "blank it".

**D-5 — Typed text is written VERBATIM, bypassing `names.dn*`.** 36 Pattern 5 (filename and tag both use
the display-translated name) governs strings the APP derived. An explicit edit is the user's exact
intent and must not be script-converted on its way to disk. The library row still renders through
`names.dnTitle` like every other row — that asymmetry is the display layer doing its existing job.

**D-6 — What "cover is synced / lyrics is synced" means.**
- Cover: the sheet passes TrackMenu's existing `activeCover` ladder (pin -> `player.resolvedCover` when
  this is the playing song -> the shared reactive cache -> `track.cover`), which `retagOne` already
  feeds to `resolveArtworkDataUrl`. Same resolver, same 6 s / 1 MB / https-only bounds, no new fetch path.
- Lyrics: whatever the app HAS — `player.current.lrc` when this is the playing song — is embedded. When
  the app has none, none are written and the file's existing lyrics are PRESERVED by omission (D-4). The
  editor never fires a network resolve to go hunting for lyrics: this is a metadata editor that must work
  offline. To sync lyrics into an old file, play the song once (which resolves them), then edit.
- This also closes a real gap: `retag.ts` never passed `lyrics` at all. Task 1 threads the field through,
  so the batch sweep gets it the day a caller has lyrics to give it.
</scope_decisions>

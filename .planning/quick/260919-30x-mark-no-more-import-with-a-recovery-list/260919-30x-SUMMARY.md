# quick-260919-30x: Mark "no more import", with a recovery list — Summary

A per-file "don't import again" mark over a new bounded localStorage record that the Phase 34 device
scan honours, with a recovery list under Settings -> Downloads; plus an optional user-typed filename
on `retagOne`, surfaced as a native-only File name field in the existing metadata sheet.

## What now happens to bytes on disk

### (a) An imported `device:` track the user marks "don't import again" — NOTHING IS TOUCHED

Traced, not asserted:

1. `TrackMenu.noImport()` calls `excludeUid(uid, label)` — a `localStorage.setItem` on
   `openmusic:import-exclusions:v1`. `import-exclusions.ts` imports nothing but itself; it has no
   Capacitor, Filesystem, MediaStore or blob-store reference of any kind.
2. It then calls `library.removeDownload(uid)` (`library.svelte.ts:278`). That method filters the
   `downloads` array, clears any unavailable mark, `save()`s, and fires `void blobStore.del(uid)`.
3. `blobStore.del` → `nativeDel(uid)` on native (`blob-store.ts:258`). Its **first statement** is
   `if (isDeviceUid(uid)) { clearStoredUri(uid); return; }` — so the two destructive calls below it,
   `Filesystem.deleteFile` (the app-private copy) and `MediaStoreSaver.deleteFromMusic` (a
   `contentResolver.delete()` that really does destroy the file), are **never reached**.
   `clearStoredUri` is a `localStorage.removeItem` on the URI index; it touches no file.

Net effect: the library row (memory + `openmusic:library:v1`) and the new exclusion record. The
user's audio file stays in its own folder, under its own name, with its own bytes, still listed by
the phone's own music app. No read, no rename, no move, no delete.

The toast says exactly this (`toast.noImportDone`: "This file stays on your phone…"), and the clause
is preserved in all 15 translations.

### (b) An app-downloaded track — the row is not offered, and nothing in this task changed its path

The menu row is gated `{#if isDevice}`, so an app download never sees it. Its removal path
(`library.removeDownload` → `nativeDel` past the device guard) is untouched 999.1-D-11 behaviour:
it deletes the two copies **the app itself created** — `Directory.Data/downloads/<uid>` and the
public `Music/OpenMusic/<name>` MediaStore entry recorded in the URI index. This task did not extend,
reuse or modify that path; `git diff` shows zero changes under `blob-store.ts` or `library.svelte.ts`.

Renaming an app download (F2) also only rewrites app-created artifacts: `retagOne` → `blobStore.put`
→ `nativePut` overwrites the uid-keyed app-private copy in place, then (36-D-19) deletes the
**recorded previous public URI** and saves one new `Music/OpenMusic/<typed name>.<sniffed ext>`
entry — one copy, not two. The delete there targets a URI the app wrote itself and recorded itself;
`linkPublicUri` refuses to put a device URI into that index, so it can never point at a user file.

## Does the exclusion survive the next device-import scan? YES — proven in tests, not by inspection

This is the whole point of F1, so it is verified at both layers rather than argued:

- **Brain** (`device-import.test.ts`, 6 new cases): `classifyRow` returns
  `{ kind: 'skip', reason: 'excluded' }`; the mark outranks a generic rule but not `outside`; the
  buckets still sum to the unique row count with `skippedExcluded` included; an **already-imported**
  marked entry is never `seen` and therefore drops through the existing D-07/D-08 lane
  (`summary.removed === 1`, no second removal path); an **incomplete** scan still keeps it listed
  (D-08 outranks the mark — a mark must not become the loophole that lets a cancelled scan delete
  rows); omitting the argument is byte-identical to today.
- **Wiring** (`device-import.svelte.test.ts`, 3 new cases, added beyond the plan): a full
  `runImport()` with a real in-memory `localStorage` does **not** bring a marked file back; a mark
  made *after* a previous run still counts (the store reads `excludedUids()` at call time, not at
  module load or mount); and `unexcludeUid` + re-scan brings it back (`added === 1`).

Without those wiring tests the feature could have been a no-op that only the pure brain believed in.

## Where rename is offered, where it is refused, and why

- **Offered:** inside `MetadataEditor`, native only, for an app-downloaded song. The sheet is opened
  from a row already gated `{#if blobPresent && !isDevice}`.
- **Refused for a `device:` track** — twice, both pre-existing: the opening row's `!isDevice` gate,
  and `retagOne`'s `if (isDeviceUid(entry.uid)) return 'device-skipped'` first statement (tested,
  including with a `filename` set). Renaming a user file means a Kotlin `MediaStore.DISPLAY_NAME`
  update, i.e. moving/renaming a file this app does not own. **No third guard was added inside the
  editor on purpose** — a redundant guard invites someone to relax one of the two that enforce it.
- **Refused on the web build** (D-8, `Capacitor.isNativePlatform()`): the web branch of
  `blobStore.put` ignores `filename` entirely (the IDB record is uid-keyed) and the browser
  Downloads copy is unreachable by any browser API. A visible field that silently does nothing is
  worse than no field.
- **The typed string can never escape:** it goes through the single `sanitizeFilename` (no `/` or
  `\` survives — blocks `../` and MediaStore RELATIVE_PATH escape, T-30x-01), an all-dots strip
  (`.`/`..` are not names), a 120-char cap, and then the extension is appended from `out.format`,
  the **sniffed container**. Typing `note.txt` yields `note.txt.m4a`; `evil/../../x` yields
  `evil_.._.._x.m4a`. Blank / whitespace / all-dots falls back to today's derived name byte for byte.

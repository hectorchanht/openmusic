<scope_semantics>
## THE LOAD-BEARING DECISION: what "remove from the download list" touches on disk

This is the part that must be right. State it in the code comments too.

### (a) An imported `device:` track — the user's own file. NOTHING ON DISK IS TOUCHED.

"Don't import again" calls the EXISTING `library.removeDownload(uid)`. That method's only disk-side
effect is `void blobStore.del(uid)`, and `blobStore.del` -> `nativeDel` has this as its **first
statement** (`blob-store.ts`, 34 Pitfall 1):

```
if (isDeviceUid(uid)) { clearStoredUri(uid); return; }
```

So for a device uid the file is **not read, not renamed, not moved, not deleted**. `deleteFromMusic`
(a MediaStore `contentResolver.delete()`, which really does destroy the file) is never reached. The
song stays in the user's Music/ or Download/ folder, keeps its name, and the phone's own music app
still lists it. The only changes are the app's in-memory + localStorage library row, and a new
localStorage exclusion record.

**This plan adds no new file-writing, file-moving or file-deleting code path of any kind.** If a task
below appears to need one, it does not ship.

### (b) An app-downloaded track — NOT OFFERED, and why.

The row is shown **only** for a device uid (`{#if isDevice}`). Three reasons, all checkable:

1. `removeDownload` on an app download already deletes the app's OWN two copies — the app-private
   `Directory.Data/downloads/<uid>` file and the public `Music/OpenMusic/<name>` MediaStore entry the
   app itself created. That is shipped 999.1-D-11 behaviour. **This plan does not extend, reuse for a
   new purpose, or change it.** (Those copies are app-created artifacts, not the user's own music —
   which is exactly why `nativeDel` deletes them and refuses a device uid.)
2. Because no file survives that delete, there is nothing left for a scan to find. An exclusion
   recorded for it would be dead state forever.
3. The label would be a lie: no scan ever imports an app-downloaded track under its own uid.

**The one residual hole, named:** the public-copy delete is best-effort and swallowed (WR-01). If it
fails, the `Music/OpenMusic/` file survives, and the next scan imports it as a `device:` track (D-16
— it matches nothing, so it imports rather than vanishing). At that point it IS a device track and
the user can mark it normally. Self-healing, no extra code.

### (c) Renaming — offered for app downloads only, never for a `device:` track.

Renaming a user's own file means a Kotlin `MediaStore.DISPLAY_NAME` column update: a native change
with its own device UAT, and it MOVES/RENAMES a file this app does not own. Forbidden here.
`retagOne` already refuses a device uid as its first statement, and the MetadataEditor row that opens
the sheet is already gated `{#if blobPresent && !isDevice}` — so the rename field inherits both
refusals with **zero new gating code**. That inheritance is the main reason F2 lives in that sheet.
</scope_semantics>

<decisions>
Recorded, not asked. Each gets a `quick-260919-30x` comment at its implementation site.

**D-1 — Persistence: a new bounded store, `src/lib/services/import-exclusions.ts`, key
`openmusic:import-exclusions:v1`.** Structurally a near-verbatim copy of `lyric-pins.ts` (which is
itself a copy of the cover-cache PIN block) — pure, node-testable, never throws, a failed write
simply does not persist. No existing key family fits: `openmusic:library:v1` is the library payload
that `setDownloads` rewrites wholesale on every import (an exclusion inside it would be clobbered by
the very pass that must read it), and `openmusic:import-rules:v1` holds generic phrase rules, not
per-file choices.

*Rejected, worth naming:* appending the filename to the existing `rules.skipRules` phrase list. Zero
new persistence and the rules UI would double as the recovery list — but skip rules are
case-insensitive substrings matched against the name AND the folder, so marking `Hello.mp3` would
also silently exclude `Hello (Live).mp3` and every file under a `hello/` folder, and the recovery
list would mix app-written entries into the user's hand-typed rules. Over-broad; not taken.

**D-2 — Bounds: `MAX_EXCLUSIONS = 500`, `MAX_LABEL_CHARS = 120`, eviction insertion-order-first.**
localStorage is a shared origin quota and the cover cache's writer swallows `QuotaExceededError`, so
an unbounded record surfaces as "covers silently stopped caching", miles from the cause (the exact
`lyric-pins` D-3 reasoning — inherit it, do not re-derive it). Worst case ~65 KB.
*Divergence from lyric-pins, deliberate:* an over-long **label is TRUNCATED, not rejected**. In
lyric-pins a half LRC is a worse lie than no pin, so it rejects. Here the label is only a human
identifier and the exclusion itself is the payload — rejecting would throw away the thing the user
asked for to protect a display string. `ponytail:` comment the 500-entry ceiling (oldest MARK is
evicted, not least-recently-used; that file then re-imports and the user re-marks it).

**D-3 — Keyed on the `device:<id>` uid.**
*Accepted failure mode, stated:* the id is the MediaStore `_ID`. A MediaStore provider rebuild
(clear-storage, factory reset, SD remount) reassigns ids, so an exclusion can (i) **lapse** — the
file re-imports and the user re-marks it, or (ii) in the pathological case **land on a different
file**, which is then silently not imported until the user opens the recovery list and allows it
again. This is not a new bug class: it is the **same accepted cost 34-D-02 already documents** —
"a like or playlist reference to a rebuilt _ID now points at a different song" — and the whole
`device-import.ts` refresh-in-place design is built on top of it.
*Why not key on the file path:* `relativePath`/`displayName` live on the `ScanRow`, are never
persisted onto the `Track`, and so **cannot be computed at the mark site** (TrackMenu has a `Track`,
not a row). Keying on path would need a new persisted `Track` field plus a migration for every
already-imported entry. It also lapses on rename/move. Not worth it.
*The mitigation is the recovery list itself* — the exclusion is visible and reversible rather than
invisible state, which is precisely why the user asked for the list.

**D-4 — Recovery list offers "Allow again" only, NOT "import this again now".** Un-excluding makes
the file eligible; the next scan brings it in, and the scan button is the section directly above on
the same page. A per-file import would need a single-row scan path that does not exist. Smaller
option taken, as instructed.

**D-5 — Rename lives inside `MetadataEditor`, not as its own menu row.** It is already the "edit this
song's identity" sheet; the filename is *derived from* the title and artist it edits
(`buildDownloadFilename(entry.artist, entry.title, out.format)` inside `retagOne`), so editing the
name beside the fields it derives from is where a user looks; `retagOne` is already the single write
path that renames the public file (36-D-19 delete-previous-URI-then-save), so a separate row would
call the same function with no extra affordance; and it inherits the `!isDevice && blobPresent` gate
for free (see scope_semantics (c)).

**D-6 — The user types a BASE name; the app appends `.${out.format}` from the SNIFFED container.**
Keeps `retagOne`'s existing "the extension comes from the sniffed container, not from a URL" rule
intact, and stops a user typing `song.txt` into a MediaStore audio entry.

**D-7 — Blank filename = today's derived name.** Matches the sheet's existing blank-means-keep
convention (1eh D-4) and makes the field a strict no-op unless used, so there is no regression
surface. The auto-derived name is shown as the input's `placeholder`.

**D-8 — The field is hidden on the web build (`Capacitor.isNativePlatform()`).** `blobStore.put`'s
web branch ignores `filename` entirely (the IDB record is uid-keyed) and the copy in the browser's
Downloads folder is unreachable by any browser API — 1eh's documented platform ceiling. A visible
field that silently does nothing is worse than no field.

**D-9 — No `*.svelte.ts` reactive wrapper for the exclusion store.** `lyric-pins` needed one because
pinned lyrics render live during playback while the pin is written from a different surface. Here the
only writer is TrackMenu and the only reader is the settings page, which cannot be mounted at the
same time. The settings page holds a plain local `$state` seeded from `readExclusions()`. Recorded so
the absence reads as a decision, not an omission.

**D-10 — Every new parameter is OPTIONAL with a default.** `classifyRow`'s 5th arg and
`syncDevice`'s `opts.excluded` default to an empty set; `RetagEntry.filename` is optional. The
existing `device-import.test.ts` and `retag.test.ts` suites and every existing call site stay
compiling and green without edits.
</decisions>

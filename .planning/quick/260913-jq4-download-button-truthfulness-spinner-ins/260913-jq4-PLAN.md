# Quick 260913-jq4 — make the download button tell the truth

Two reported symptoms, two different root causes, one button.

## A. First tap toasts "no audio available" instead of showing a spinner

`gated('download', doDownload)` pre-resolves the stub and then vetoes:

```ts
const resolved = await ensureTrackDetails(track);
if (!resolved.audioUrl) { toast.show(t('toast.noAudio')); return; }   // doDownload never runs
```

That pre-resolve is both **redundant and wrong for download**:

- `downloadTrack` does its OWN resolve, forced fresh, at `settings.downloadQuality` — a different
  tier from the streaming default `gated()` resolves at. So the veto can reject a download that
  would have succeeded.
- `downloadTrack` already brackets `library.beginDownload` / `endDownload` **synchronously before
  its first await**, so the per-uid spinner covers the real operation on the same tick.
- `downloadTrack` never throws and returns `'no-audio'` itself when there genuinely is none.

So `gated()` adds a second resolve whose only distinct effect is a premature error toast.

**Fix:** Download stops going through `gated()`. Remix and Detail keep it — they genuinely need a
resolved `audioUrl` in hand before they can run.

## B. "Downloaded" shows even when nothing was saved

`library.isDownloaded(uid)` is list membership, and `library.addDownload(r)` runs **before** the
fetch — deliberately (DL-BUG-01: a failed download still leaves the song re-streamable). On top of
that, `saveBlobToDisk` uses an `<a download>` click, which reports success even when the user
cancels the browser's save dialog — the web platform gives no cancel signal.

So the list cannot answer "is this downloaded". The **offline blob** can: it is what makes an
offline play work, and it is the only artifact the app can actually verify.

**Fix:** the Check state asks the blob store, not the list. The downloads *reference list* keeps
its current meaning and is not touched.

## Tasks

### T1 — `blobStore.has(uid)`

**files:** `src/lib/services/blob-store.ts`, `src/lib/services/blob-store.test.ts`

**action:** Add an existence probe next to `get`, same never-throws / SSR-guarded posture, exported
through the `blobStore` namespace:

- web: IDB `getKey(uid)` — existence without materializing a multi-MB Blob (the whole point; a menu
  open must not pull a FLAC into memory).
- native: `Filesystem.stat` on the app-private path, gated on `size >= MIN_BLOB_BYTES` (the same
  31-D-13 floor `get`/`nativeGet` apply, so a truncated write reads as absent on both platforms).
- any error / no IDB / SSR → `false`.

**verify:** `pnpm test` — new cases in blob-store.test.ts: web hit, web miss, native hit, native
too-small, native throw.

**done:** `blobStore.has` exists, is cheap, and never throws.

### T2 — Download no longer routed through `gated()`

**files:** `src/lib/components/TrackMenu.svelte`

**action:** Replace both Download call sites (header icon + list row) with a `startDownload()` that
calls `doDownload(track)` directly. `doDownload` takes the stub now — `downloadTrack` resolves.
Dedupe on `library.downloading.has(track.uid)` (the D-03 equivalent for this path). `dlBusy` /
`hdBusy` read `library.downloading` only; `inFlight` stays for Remix and Detail.

Comment the reversal against D-02: the gated resolve-then-act pattern still stands for the other
two rows, Download opts out because its service already owns the resolve.

**verify:** tap Download on an unresolved stub — spinner appears on the same tick and stays for the
whole operation; no "no audio available" unless `downloadTrack` returns `'no-audio'`.

**done:** One resolve per download, spinner spans it, the toast comes from the real result.

### T3 — Check reflects the offline copy

**files:** `src/lib/components/TrackMenu.svelte`

**action:** Local `blobPresent = $state<boolean | null>(null)` — probed via `blobStore.has` in a
`browser`-guarded `$effect` keyed on `open` + `track.uid`, with an `alive` flag so a stale probe
cannot land on a newer track. Re-probe after `doDownload` resolves. Both Download surfaces render
Check only on `blobPresent === true`; `null` (not yet known) renders the normal Download affordance.

**verify:** download a song then cancel the browser save → the menu still offers Download, not a
greyed Check. Complete a save → Check.

**done:** Check means the offline copy exists.

## Out of scope

- `library.isDownloaded` and the Downloads shelf keep list semantics (a different question:
  "has the user asked for this offline"). Migrating other surfaces to the blob-backed check is a
  follow-up, not this fix.
- Detecting a cancelled browser save directly — the platform exposes no signal; the blob check is
  the achievable answer.

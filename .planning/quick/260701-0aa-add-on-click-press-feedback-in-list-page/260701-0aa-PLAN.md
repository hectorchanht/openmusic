<objective>
Add three pure-UI press/selection affordances to the song lists and grids (no playback,
data, or persistence changes):

1. **List-view active/selected row highlight** — the row of the currently-playing track
   gets a persistent light-grey `--color-surface` background. Driven by the EXISTING
   currently-playing state (`player.current.uid`), NOT a new selected-id — see the
   interpretation note below.
2. **List-view tap bounce** — pressing a song row briefly shrinks it (cover + row) then
   springs back.
3. **Grid-view tap bounce** — same shrink-then-spring on grid cover tiles.

Purpose: native-app-like tactile feedback so taps register visibly and the active song is
obvious in a list. Mobile-first (must work on touch, not just hover).

Output: one new reusable `use:tapBounce` action + shared keyframes in app.css, wired into
the list views (search, library, CompactRow) and grid tiles (home `.tile`/`.album`).
</objective>

<interpretation>
The task wording ("clicked song row shows a light grey background to indicate selection/active")
maps to the player's currently-playing track. The project ALREADY tracks this as
`player.current` (a `Track | null` with `.uid`). Per the task's own guidance ("prefer reusing
existing currently-playing state if present"), we drive the highlight off `player.current?.uid`
and do NOT introduce a new selected-id. Rationale: a separate "last-tapped" id would diverge
from the playing track on auto-advance and feel wrong; the playing row IS the active row.

CRITICAL constraint discovered in the codebase (MENU-03 / D-12): `.tile`/`.album` already have
`:active { transform: scale(0.96) }` but DELIBERATELY gated behind `@media (hover: hover)`,
because on touch a CSS `:active` LATCHES under a held finger while a long-press opens the
track menu. We must NOT remove that gate. Instead the tap bounce is a ONE-SHOT keyframe
animation triggered on `pointerdown` and cleared on `animationend` — it springs back on its
own regardless of whether the finger stays down, so it cannot latch. The existing
hover-only `:active` scale is left untouched for mouse users (the keyframe handles touch).
</interpretation>

<task type="auto">
  <name>Task 1: Create the reusable use:tapBounce action + shared keyframes</name>
  <files>src/lib/actions/tapBounce.ts, src/app.css</files>
  <action>
    Create `src/lib/actions/tapBounce.ts` exporting `tapBounce`, a Svelte `Action<HTMLElement>`
    (mirror the structure of longpress.ts: a function returning a `{ destroy() }` object;
    use `import type { Action } from 'svelte/action'`). Behavior:
    - On `pointerdown`, add a CSS class `tap-bouncing` to the node. If the class is already
      present (a rapid re-press mid-animation), first remove it and force a reflow
      (`void node.offsetWidth`) before re-adding, so the keyframe restarts cleanly.
    - Listen for `animationend` on the node; when the event's `animationName === 'tap-bounce'`,
      remove the `tap-bouncing` class. (Guard on animationName so an unrelated animation on a
      descendant — e.g. a marquee — does not clear it early.)
    - Reduced-motion: gate the class-add behind a `prefers-reduced-motion: no-preference`
      check via `window.matchMedia('(prefers-reduced-motion: reduce)').matches` — when reduce
      is set, do nothing (no class, so no scale). (The CSS keyframe is ALSO reduced-motion
      guarded for defense-in-depth; this just avoids dangling classes.)
    - The action does NOT call preventDefault, does NOT stop propagation, does NOT touch
      click/longpress — it is purely visual and must compose with the existing use:longpress
      and onclick handlers already on these buttons.
    - `destroy()` removes both listeners.
    Then in `src/app.css` add a shared keyframe + class near the existing `@keyframes sk-shimmer`:
    - `@keyframes tap-bounce` that scales from 1 → ~0.94 → back to 1 (a quick down-then-spring;
      e.g. 0% scale(1), 40% scale(0.94), 100% scale(1)).
    - `.tap-bouncing { animation: tap-bounce 0.22s ease; }` — short, single-shot.
    - The bounce target must have `transform-origin: center` and (for tiles) a transition that
      does not fight the keyframe; `.tile`/`.album` already have `transition: transform 0.12s
      ease` which is fine (the animation overrides during play). For `.row`/`.crow` (no transform
      transition today) no extra transition is needed — the keyframe animates transform directly.
    - Add a `@media (prefers-reduced-motion: reduce)` block setting `.tap-bouncing { animation: none; }`.
    Do NOT scope the keyframe to a component `<style>` (Svelte would mangle the name); it lives
    in the global app.css so the action's class name matches across all call sites.
  </action>

<objective>
Two independent features on the existing lyric machinery.

**F1 — lyrics picker + reloader in the song menu.** A `Fix lyrics` row in `TrackMenu` opens a sheet
listing one row per source that returns an LRC for this song. Tapping one persists it per-uid and
every lyrics surface repaints. The sheet re-walks the sources on every open (that IS the reloader),
offers a Retry row on a dry walk, and a Use-automatic row that drops the stored pick.

**F2 — current lyric line under the collapsed play bar.** An opt-in setting makes the docked Nowbar
replace its artist line with the currently-sung lyric line.

Purpose: the lyric chain is first-source-wins and sometimes wins wrong (wrong song, wrong language,
an instrumental's LRC). Today the user has no way to correct it. And the lyric is the one thing worth
seeing without expanding the player.

Output: one pure bounded pin store + its reactive wrapper, one new catalog entry point sharing the
existing walk, one shared pure active-line helper, one menu row + sheet, one Nowbar line, one setting,
7 i18n keys across 15 dictionaries.
</objective>

<decisions>
Recorded, not asked (the developer asked for the obvious option taken autonomously). Every one of
these gets a `quick-260919-1we` comment at the site that implements it.

**D-1 — the pick is stored PER-UID in its own namespaced key `openmusic:lyric-pins:v1`.**
Per-uid, not per name-key: the cover pin is per-uid, the menu already disables pin-style actions on a
uid-less name stub, and a name-key pin would spill one song's pick onto every same-titled variant
(the exact bug the cover cache's name layer is documented to cause when a pin enters it). Its own key
family, mirroring `openmusic:cover-pins:v1` — not a new storage LAYER, the same layer one key over.

**D-2 — the stored value is the LRC TEXT, not the source id.** Storing "user picked kuwo" would make
every replay depend on kuwo answering, and would silently show different lyrics when upstream drifts.
The text is the user's choice; persist the choice.

**D-3 — the pin record is BOUNDED: ≤ 20 000 chars per entry, ≤ 100 entries.** localStorage is shared
with the cover cache, whose writer swallows `QuotaExceededError` — one unbounded LRC record would
silently stop all cover caching app-wide. This is the one way this feature could break something
unrelated, so it is capped at the writer.

**D-4 — the pin is applied at READ time, not by mutating `player.current`.** `player.svelte.ts` has
seven `this.current = …` sites; four of them assign a whole fresh object and would clobber a pin
applied at any of the other three. Layering the pin into a reactive READ (exactly what
`readCoverByUidOrName` does for cover pins) fixes every surface at once with no player surgery — and
it is what makes the pin beat Phase 37's embedded-LRC enrichment by construction, because
`enrichFromLocalFile` writes `current.lrc` while the read order is `pin ?? track.lrc`. Read order is
**pin → track.lrc → null**, one definition, three call sites.

**D-5 — candidates are one row per SOURCE that actually returns an LRC**, picked by the same
`matchKey` identity + `scoreMatch` ranking `lyricWalk` already uses, skipping `LYRICLESS_SOURCES`.
Identical shape to the download-source picker. No second ranking algorithm.

**D-6 — the "reloader" is the sheet open itself.** Nothing caches a resolved LRC client-side
(`apiFetch`'s GET dedupe is in-flight only), so every open re-walks live. The two explicit
affordances are therefore the ones that are NOT redundant: a `Retry` row shown only on a dry walk,
and a `Use automatic` row shown only when a pin exists. A third always-visible "Reload" button would
re-run the walk that just ran.

**D-7 — `nowbarLyrics` defaults to FALSE.** It replaces information already on screen with different
information; the precedent for an opt-in display toggle in the same settings group is
`showQualityTag: false`. A user who never opens Settings sees exactly today's Nowbar.

**D-8 — the lyric line REPLACES the artist line in the docked Nowbar; it never adds a third row.**
The bar is a fixed `--nowbar-h`. A third line squeezes the other two, and a conditional third line
shifts the layout every time the LRC has a gap — the exact flicker the brief forbids. Replacing means
zero layout change, and the artist is one tap away in the hero. Embedded variant (`variant === "embed"`,
mounted inside NowPlaying above the open lyrics pane) is excluded: duplicating the current line
directly above the full lyrics pane is noise.
</decisions>

In the `<script>`, below the existing `npKey` derived:

```
const lyricLines = $derived(parseLRC(readLyrics(player.current) ?? ""));
const lyricText = $derived.by(() => {
    if (!settings.nowbarLyrics || variant !== "docked") return "";
    const { idx } = activeLineAt(lyricLines, player.currentTime);
    return idx >= 0 ? lyricLines[idx].text : "";
});
```

Three things this shape is doing deliberately, each worth a `quick-260919-1we` comment:
1. **`parseLRC` only — no `reorderPairs` / `splitParenLines`.** One line in a 44px bar has no room for
   an original/translation pair, and those two exist to serve the stacked lyrics pane. Raw parsed
   lines are the right granularity here, and they cost one pass over the string per TRACK (the derived
   depends on the lyric string, not on `currentTime`).
2. **The early return gates the whole scan**, so with the setting off this costs one boolean read per
   tick and nothing else. `variant !== "docked"` is D-8's embed exclusion.
3. **It returns a STRING.** `player.currentTime` changes ~4×/s, so the derived re-evaluates ~4×/s —
   but Svelte 5 writes the DOM only when the value actually changes, so the repaint happens on LINE
   change, exactly as the brief requires. No `$effect`, no `logAction`, nothing on the timeupdate
   firehose.

`parseLRC` silently drops every line with no timestamp, so a plain-text (unsynced) LRC yields `[]` →
`lyricText` is `""` → the artist line renders unchanged. Same for an instrumental and for no lyrics
at all. That is the whole degrade story and it needs no extra branch.

In the template, inside the existing `{#key npKey}` block, `.np-artist`'s inner `.marquee-inner`
becomes a two-way branch (D-8 — REPLACE, never a third row):

```
{#if lyricText}
    {#key lyricText}
        <span class="np-lyric" in:fade={{ duration: xfadeMs }}>{lyricText}</span>
    {/key}
{:else}
    {names.dnArtist(np?.artist ?? "")}
    {#if player.error}· <span class="err">{tMaybeKey(player.error)}</span>{/if}
{/if}
```

Reduced motion is already handled: `xfadeMs` is the file's existing derived and is `0` under
`settings.reduceMotion` OR the OS `prefers-reduced-motion` query — reuse it, do not add a second
motion gate. Use `in:` only, no `out:` — an outgoing line animating while the incoming one arrives in
the same 11px row reads as a smear.

Keep the `player.error` branch inside the `{:else}` only: a playback error must never be hidden behind
a lyric, but when there IS an error the Nowbar is not the surface to show the song's poetry on.

Add a `.np-lyric` rule next to `.np-artist`: same `font-size: 11px`, `color: var(--color-text)`,
`opacity: 0.9`, `white-space: nowrap; overflow: hidden; text-overflow: ellipsis;`. No height, no
margin, no padding — the row geometry must not move between the two branches.

New imports: `parseLRC` and `activeLineAt` from `$lib/services/lrc`, `readLyrics` from

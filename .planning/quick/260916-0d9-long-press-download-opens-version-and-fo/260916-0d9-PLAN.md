<design_answers>
The five design questions, answered from the code (each is a comment target — tag `quick-260916-0d9`):

Q1 CANDIDATES — reuse `fetchVariants(track, signal)` (services/variants.ts, Phase 26-08). It already
does the ONE all-source `searchAll` and matches the same song via `groupVariants` + `sameSongKey`
(the dedupe.ts identity). `collapseVariants` (dedupe.ts) removes intra-source duplicates exactly as
VersionPicker does at render. `collectCoverCandidates` is cover-specific and is NOT used. No new
matching code anywhere — the only new pure function is a 4-line list assembler.

Q2 PROBE COST — the sheet opens IMMEDIATELY with the own-source row (its `probeDownload` memo key
`uid|downloadQuality` is the one the main Download row already filled → zero network) and a spinner
line while `fetchVariants` runs (searchAll is D-04 TTL-memoised). Then every other candidate is
probed through the existing `mapWithConcurrency(items, 2, fn)` (services/discovery.ts) — 2 in
flight, each probe = 1 governed `ensureTrackDetails` + 1 raw HEAD/Range — so at most 2 of the 8
`apiFetch` slots are ever held by the picker (api-fetch-flood history: an uncapped fan-out froze this
app). Each row fills as its probe lands (per-item write inside `fn`); the sheet's AbortController is
threaded into every probe and aborted on close. A total probe miss renders 'Unavailable'.

Q3 FORMAT — ONE list, not two axes. `effectiveQuality` collapses 'auto' to a tier; each adapter's
ladder then yields ONE url per source at that tier, and the container is a property of that url
(`containerFromContentType ?? containerFromUrl`). So "format" is chosen BY choosing the source row
(kuwo → FLAC 38 MB vs netease → 320K 8 MB). No format dropdown. Offering each source's full tier
ladder (kuwo FLAC AND kuwo 320) would need a `tier` parameter on `probeDownload` (its memo is keyed
by the settings tier) and 3× the probes — DEFERRED, recorded in the deferred-items file.

Q4 GESTURES — `use:longpress` goes on the `.mi` Download button; `use:dragClose` stays on the parent
`.menu`. They are mutually exclusive by the SAME 8px threshold: any move >8px cancels the longpress
timer (longpress.ts `move`) and is the only thing that starts a drag (dragClose.ts `move`,
`rawDy > DRAG_START`); a stationary hold never starts a drag. The trailing native click is eaten by
longpress's DOCUMENT-capture suppressor (quick-260913-p2k moved it to document precisely so a sheet
mounted under the finger is covered) — so `onclick={startDownload}` does NOT also fire. Note the
existing `startDownload` early-returns while `library.downloading.has(uid)`, a second guard.
Discoverability: a trailing `ChevronDown size={14}` inside the row's existing `.count` slot + the
hint in `title`/`aria-label`. Right-click on desktop is preventDefault'd by the action (unchanged).

Q5 IDENTITY — the download is recorded under the ORIGINAL track. New `downloadTrack(track,
{ audioFrom: donor })`: `r = { ...track, audioUrl: donor.audioUrl, quality: donor.quality,
qualityLabel: donor.qualityLabel, resolvedAt: donor.resolvedAt, detailsLoaded: true, lrc: track.lrc
|| donor.lrc }`, SKIPPING both `reuseCurrent`/`reuseInput` and the re-resolve. Why skip: with the
original uid, `reuseCurrent` would fire whenever this song is playing and silently substitute
`player.current`'s url for the row the user chose; and a re-resolve at the settings tier could hand
a cellular user a 52 MB FLAC the row never showed. Consequences that line up by construction:
`library.beginDownload/endDownload/setDownloadProgress(track.uid)` = the menu row's spinner;
`library.addDownload(r)` = original identity in the downloads list; `blobStore.put(r.uid)` = original
uid; `player.play(original)` → `library.isDownloaded(target.uid) && blobStore.get(target.uid)` →
plays the chosen source's bytes. Filename + tags use the original `artist`/`title` (dn*). A donor
url that went stale (sheet left open >15 min) fails at `fetch` → 'failed' → the existing
"Couldn't save · kept in Library" toast — the same degrade as any CDN refusal, no new path.
</design_answers>

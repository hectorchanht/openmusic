<objective>
A song the client resolved a cover for still unfurls a blank branded card: `/api/og` re-resolves the
cover server-side from artist+title TEXT through a chain that is independent of the client's cover
authority. Reported case: 你瞞我瞞 / 陳柏宇 — Quinquennium art on the hero, the Nowbar and the
Downloads rows, nothing on the WhatsApp card.

The client already KNOWS the right cover when the user taps share, so carry a SHORT COVER ID in the
link and let `/api/og` rebuild the image URL from its own fixed per-tier template.

Locked user directives, in order given: (1) bring the carrier back, validated — reversing OG-EP-01 /
T-24-08; (2) it must be a short cover id, not a URL — "make sure such cover id is short, and clear
enough for fast resolving"; (3) "kuwo and itunes must be covered too, don't leave gaps". All four
tiers get a tag. None of the three is up for re-litigation here.

The id shape is a security UPGRADE over both the retired `?c=` carrier and a validated-URL carrier:
the host allow-list stops being a check an attacker can probe for parser bypasses and becomes
STRUCTURAL — scheme, host and path shape are literals in our own source, and what crosses the
boundary is an id matched against an anchored per-tier pattern.

Purpose: one song, one cover — in the app AND in the messenger card, for every tier.
Output: a validated `ci` token end-to-end (share → link → loader → /api/og → rebuilt URL → streamed
bytes), plus the client-side iTunes id retention that tier needs, with the existing tier chain
untouched as the fallback for every link that carries nothing usable.
</objective>

character classes, per-tier max length, global cap 64 chars. No `/`, no `.` outside the one place a
tier's extension lives, no `%`, no `\`, no `@`, no empty segment can be expressed — traversal is
UNGRAMMATICAL rather than filtered.

## Size: PINNED server-side for all four

Every tier's size is pinned in the template, never carried: it keeps the token shorter and removes a
field an attacker could play with, and the card wants card-size art (~500–600 px) rather than the
client's 1000/1200 px tile art. Consequence for the round-trip test, stated plainly because it is
asserted both ways:
- **Byte-identical** round trip when the client's stored URL is already at the pinned size — the
  normal case for kuwo (its search body serves `/600/`) and for a Deezer `cover_big`.
- **Size-normalized** round trip otherwise (client tiles prefer Deezer `cover_xl` 1000×1000 and
  iTunes `1200x1200bb`): the rebuilt URL is the same asset at card size. Assert this explicitly as
  its own case — `coverToken(anySizeVariant)` must yield the SAME token, and
  `coverToken(rebuild(token)) === token`. Token-level identity is the invariant; URL-level identity
  holds only for already-card-size inputs.

## The one asymmetry: `i` costs a lookup

`d`/`l`/`k` rebuild purely (0 subrequests). `i` needs ONE bounded GET to a FIXED host
(`itunes.apple.com/lookup`) because the mzstatic path is not derivable from any short id. Weigh it
honestly: that is 1 subrequest against a fixed, allow-list-irrelevant host (the lookup is JSON, not
the image), versus today's up-to-FIVE-lookup text chain — still a large net win on "fast resolving",
and it is deterministic (an id, not a text search that can match the wrong album). Budget:
`TOKEN_RESOLVE_MS` (1500) with `retries=0`, so the token path's worst case is 1500 + IMAGE_MS
(2500) ≈ 4 s, inside the 3–10 s crawler budget. A lookup miss/failure routes to the branded card on
the same rule as every other tag (D1) — never to the tier chain, never a stacked second budget. The
lookup result is NOT written to the resolve cache (D2); the bytes layer still caches the image under
the `ci` key, so a repeat crawl of the same link costs zero lookups.

## Still out of grammar, by construction
netease / qq / joox cover hosts. They are on NO existing per-tier allow-list, so a tag for them
would WIDEN the set of hosts this endpoint fetches. The carrier may change WHICH allow-listed host
is picked, never the SET. Such a cover yields no token → tier chain → today's behaviour.

<decisions>
D1. Pattern failure (or an `i` lookup miss/failure) falls through as follows: a token that fails its
    pattern → the tier chain, zero cost. A token that rebuilds and passes its allow-list but whose
    image fetch fails, or an `i` lookup that misses → the branded card via the existing streamImage
    failure path, NOT the tier chain. A fall-through there would stack TOKEN_RESOLVE_MS +
    IMAGE_MS + OG_RESOLVE_MS + a second image fetch ≈ 11 s, past the 3–10 s crawler budget
    30-RESEARCH §D records. Put the arithmetic in the code comment.

D2. A carried token NEVER touches the resolve cache (neither read nor write). It is used after the
    bytes-layer lookup and instead of the resolve layer. Anti-poisoning: the resolve entry is keyed
    on normalized TEXT and shared by every requester, so letting request-supplied input write it
    would let one crafted link change what everyone else's carrier-free crawl resolves. The bytes
    layer is keyed on the request URL as-is (`ownOriginCacheKey(url)`), so each `ci` is its own
    entry. `ownOriginCacheKey` stays the ONLY key builder.

D3. The param is `ci` (cover id), NOT `c`. The legacy `/song/[slug]` route already reads `?c=`
    meaning "a full cover URL"; reusing the name for a different grammar is how two carriers quietly
    get confused for one.

D4. `songShareUrl(t, token?)` takes the TOKEN, not a URL. The caller derives it with the exported
    `coverToken(url, id?)`. One grammar, one place, and the iTunes tag needs an id the URL cannot
    supply — a URL-only parameter could never express it.

D5. iTunes id retention rides the EXISTING cover-cache entry object (`{u,t}` gains an optional `i`),
    not a new store and not string-packing. The entry is already an object with a legacy bare-string
    form, so an added optional field is backward compatible by construction: every pre-existing
    entry simply has no `i`, and `coverToken(mzstaticUrl, undefined)` returns null → no carrier →
    today's behaviour. THE HONEST COST (asked for, so stated): this is the most expensive part of
    the plan — it changes `itunesSongCover`/`itunesArtistCover` from `string|null` to
    `{url,id}|null`, which is mechanical at the two cover-backfill call sites but churns ~25
    `mockResolvedValue('https://…')` sites across cover-backfill.test.ts and itunes-cover.test.ts.
    That is more churn than tags `d`+`l`+`k` combined. It is planned rather than dropped because
    the directive is locked; the alternatives were all worse (a module-scope URL→id memo does not
    survive a reload, which is exactly when a user shares; a parallel token store duplicates
    cover-cache's three key families and its TTL/eviction).

D6. Album/artist entity links (`entityCardUrl` + the entity loaders) stay OUT of scope — four more
    files for a surface the report does not name. The `/api/og` half is type-agnostic, so adding an
    entity carrier later is one lookup + one argument per surface.

D7. The legacy `/song/[slug]` route's pre-existing `?c=` URL carrier is NOT touched. It only EMITS
    the URL into a meta tag (the crawler fetches it, we never do) — the posture its own header
    documents.

D8. Two functions, one grammar, two modules: `coverToken(url, id?)` (client, pure, `share.ts`) and
    `resolveCoverToken(token, signal)` (server, owns the templates, `og-cover.ts`). They are pinned
    together by a round-trip test importing BOTH — that test IS the anti-drift mechanism and is not
    optional (T-3uo-08).
</decisions>

| recipient's crawler → `/song/{artist}/{title}?ci=` | anyone can hand-craft this URL; `ci` is fully attacker-controlled |
| `/api/og?ci=` → outbound fetch | the only place request-supplied input influences an outbound request |
| iTunes lookup JSON → rebuilt artwork URL | third-party JSON chooses the path of the image we then fetch |
| upstream CDN → cached response | third-party bytes and headers enter our cache |

<design_decisions>
Read these before touching anything. Each was derived from the code, not assumed.

**Q1 — Collecting candidates.** `resolveTrackChain` (cover-backfill.ts:146) is sequential first-solid-wins and is the fast path for lazyCover, backfillCovers, resolveCoverForTrack and healCover. It is NOT touched. A NEW export `collectCoverCandidates(track, signal)` in the same file runs the three tiers IN PARALLEL (`Promise.all` over three never-throw closures, each wrapped by the existing module-scope `tier()`-style try/catch) using the SAME service functions the chain already imports: `deezerSearchTopN(term, 5, signal)` (already exported, 6h client TTL — yields up to 5 Deezer covers, so `deezerSongCover` is not needed), `itunesSongCover(artist, title, signal)` (top-1; iTunes only exposes `fetchTopArtwork` privately — multiple iTunes hits would need a new fetch, deferred), and `searchAll(term, 1, {}, signal)` whose `interleaved` tracks each carry `source` + `cover` — every CN source labelled for free. Shared code = the imports + `hasHttpsScheme`; nothing in the chain changes, and the collector is only ever called from the picker's tap handler (same opt-in posture as `openVersions` / T-26-10-02: never on menu open).

**Q2 — Stickiness vs self-heal.** Decision: a pin is immune to every RESOLVER PREFERENCE (Deezer HQ upgrade, Last.fm hi-res swap via adoptCover, attached album cover, inline track.cover) but NOT to a genuine dead URL. When `healCover` probes the displayed cover and it fails to load, and that URL equals the pin, the pin is REMOVED (`unpinCover(uid)`) before the existing evict + re-resolve runs. Why: a pin identifies a URL, not an image; once the URL 404s the pin can no longer deliver what the user chose, and keeping it would re-create the exact "black hero" bug 20e fixed, on every replay, forever. This is explicit (comment tagged quick-260915-w4f, a dedicated test) and narrow: only a failed image load unpins; no code path unpins because a resolver found something "better". Rows do not probe the pin (pickRowCover is a pure read) — a dead pin on a row shows the gradient until the song is played and healCover catches it. Accepted.

**Q3 — Which cache layer.** NEITHER of the three families. A pin goes to its own localStorage key `openmusic:cover-pins:v1` (flat `Record<uid, url>`), implemented as three functions inside cover-cache.ts (same try/catch idiom, same file — no new module). Reasons, in order: (a) the name layer `<matchKey>` is shared across uids — writing it would push one user's pick onto every same-named song (covers, live versions, other sources), so `writeCoverBoth` is wrong here; (b) even uid-only inside `openmusic:cover-cache:v1` inherits the 14-day read-side TTL, the 2000-entry oldest-first LRU eviction and `clearCoverCache()` — three ways a deliberate pin gets SILENTLY wiped; (c) separate storage makes the pin immune to every existing cache writer (`writeCoverBoth`, `resolveCoverForTrack`, `resolveDeezerHQ`, `removeCoverBoth`) with zero changes to them. The pin is user intent, not a cache.

**Q4 — Reactivity.** `pinCover(uid, url)` in cover-version.svelte.ts = `setPinnedCover` + `bumpCoverVersion()`; `unpinCover(uid)` = `removePinnedCover` + `bumpCoverVersion()`. The new reactive reader `readPinnedCover(uid)` calls `coverVersion()` first (same idiom as readCoverByUidOrName), and `readCoverByUidOrName` itself becomes pin-first, so every surface already bound to `coverVersion()` repaints. bumpCoverVersion is rAF-coalesced with a sync fallback in node — unchanged.

**Q5 — Hero + OS media card.** Still true in effect: `NowPlaying.effectiveCover` = `player.resolvedCover ?? readCoverByUidOrName(...)` (NowPlaying.svelte:536) and `syncMetadata` = `this.resolvedCover ?? readCoverByUidOrName(...)` (player.svelte.ts:1395); Nowbar = `player.resolvedCover ?? np.cover`. `resolvedCover` is seeded in `play()` from `attachedCoverFor(track) ?? track.cover ?? cache` (:3200) and in `restore()` from `target.cover ?? cache` (:574), so a cache-level pin loses to `track.cover` on those three surfaces AND is overwritten in the uid cache by the Site-A `writeCoverBoth` on the next line. Handled in Task 2: (1) both seeds read `getPinnedCover(uid)` FIRST; (2) the Site-A write is skipped when pinned (never leak the pin into the name layer); (3) `upgradeCoverAsync` is gated off for a pinned uid; (4) `adoptCover` refuses any URL that is not the pin and skips its `writeCoverBoth` when pinned; (5) the picker calls `player.adoptCover(uid, url)` after `pinCover` so, when the pinned song IS current, resolvedCover + a FRESH MediaMetadata are written immediately (adoptCover is already "the ONE seam" for exactly this — reuse, no new player method); (6) the device-file embedded-art branch (:794) yields to a pin.

**Rows and tiles also read `track.cover` AHEAD of the cache.** `pickRowCover(resolved, seeded, cached)` = resolved || seeded(track.cover) || cached at 9 call sites, plus NowPlaying `cellBg` and three home-page reads. A pin must beat `track.cover`, so `pickRowCover` gains a LEADING `pinned` parameter and every call site passes `readPinnedCover(uid)`. This is the one unavoidable sweep; each edit is one line.

**Security.** The picker introduces NO new image origin: Deezer URLs are host-allowlisted at the edge proxy (`safeImageUrl` / DEEZER_IMAGE_HOSTS), iTunes mzstatic URLs are what `itunesSongCover` already paints app-wide, CN URLs are the `track.cover` every row already paints. The collector applies the existing client gate `hasHttpsScheme` to every candidate (T-0bb-01). Thumbnails render as `<img src>` attributes (never CSS url() — T-rvy-01). `setPinnedCover` also refuses non-https. Do NOT import `proxy/safe-image-url.ts` client-side — it is the edge control and its allowlist would wrongly reject CN CDN hosts.
</design_decisions>

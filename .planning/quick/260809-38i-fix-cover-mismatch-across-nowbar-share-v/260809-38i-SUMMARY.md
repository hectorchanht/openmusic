# Quick Task 260809-38i: Fix Cover Mismatch Across Nowbar / Share / Card + Share Autoplay Summary

One cover per song across hero, Nowbar, lock screen and the messenger card — via a single
`player.adoptCover` promotion seam and a probe-backed, key-gated Last.fm tier in `/api/og` — plus
share links that start no audio until the user taps play.

## What Shipped

### Task 1 — `player.adoptCover`, the one promotion seam (`132c6e1`, RED `e71bdef`)

The Last.fm hi-res swap lived in a component-local `$state` inside `NowPlaying.svelte`, so it won on
the hero ONLY: `Nowbar.svelte:124` reads `player.resolvedCover ?? np?.cover` and the OS media card
reads `resolvedCover ?? readCoverByUidOrName(...)` — both were structurally blind to it, and the
shared cover cache never learned the better art. One song, three covers. That was the reported bug,
and the plan's diagnosis was confirmed by trace before any edit.

- `player.adoptCover(uid, url)` — guards in order: uid identity (a stale enrichment landing after a
  track change is discarded, mirroring `healCover` step 1) → `httpsOnly` (T-0bb-01) → same-url
  idempotence. Then `resolvedCover = url`, `adoptedCoverUid = uid`, `writeCoverBoth(...)` (which
  bumps the reactive signal itself — no Site-C double-write), and a FRESH `MediaMetadata`. Never
  throws; it is called from an `<img>` `onload` handler.
- `private adoptedCoverUid` (plain field, house rule for internal supersedence flags), cleared at
  `play()` entry beside `healProbed.clear()`.
- `upgradeCoverAsync` now bails on `this.adoptedCoverUid === resolved.uid`, so a slow Deezer HQ
  upgrade cannot overwrite a cover the hero already verified.
- `NowPlaying.svelte`: the local swap field is gone (declaration, per-uid reset, the `??` head of
  `effectiveCover`, and the healCover opt-out). `maybeSwapCover` now calls `player.adoptCover`. What
  the swap MEASURES is unchanged — still the candidate against `forTrack.cover`, the raw source
  cover — only the destination moved.

The healCover opt-out was deleted rather than moved: an adopted cover is `onload`-verified before it
is committed, so `healCover`'s probe takes its zero-network `alive → return` fast path.

### Task 2 — key-gated Last.fm tier in `/api/og` (`c01288d`, RED `ba1464f`)

**PROBE GATE: PASSED.** Against production, `track.getinfo` for 方大同 / 紅豆 returned
`https://lastfm-img.freetls.fastly.net/i/u/300x300/95f31bcdc1e942d3c24daa08dbf0e654.png`. Verified
it is the SAME asset the client hero uses, not merely a plausible one: `album.getinfo` for the
song's album (`The Soulboy Collection`, read from a live kuwo search) returned the identical hash
`95f31bcdc1e942d3c24daa08dbf0e654`. Fetched and viewed the image — a genuine 方大同 album cover.
One subrequest, exact parity with the hero.

- `safeLastfmImageUrl` — the fourth per-tier allow-list, deliberately separate from the
  Deezer/iTunes/kuwo siblings (T-wv8-05): https only, hosts `last.fm` / `*.last.fm` /
  `*.fastly.net`, CSS/attribute breakers rejected, and the grey-star hash
  `2a96cbd8b46e442fc41c2b86b821562f` rejected at the allow-list itself (ENRICH-02 / D-04 g2).
- `lastfmTier(key)` — ONE `fetchWithRetry(..., 0)` under `TIER_MS.lastfm = 900`; reads
  `track.image[]` then `track.album.image[]` (the exact preference `api/lastfm/info/+server.ts:249`
  uses), largest by size rank. No image / placeholder-only → `miss`; non-ok / malformed / Last.fm's
  own `{error}` envelope / drift → `error`. The key is never logged and never leaves the edge.
- `resolveCoverTiered` takes an optional 5th `lastfmKey`. `/api/og`'s `GET` destructures `platform`
  and passes `(platform?.env as Env | undefined)?.LASTFM_KEY`.

### Task 3 — share links do not autoplay (`25b83a4`)

Deleted `void resolveAndPlay();` from `onMount` in both share pages. The `retry` binding stays and
the existing "Play on openmusic" control runs the identical resolve on user intent, so `status`
holds at `'idle'` until the tap — no status line, and no path can strand it at `'resolving'`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The Last.fm tier had to run ABOVE the convert-first t2s pass, not inside the tier loop**

- **Found during:** Task 2, GREEN — a test asserting the upstream URL carries the encoded input title
  failed with the Simplified form.
- **Issue:** The plan placed the tier "FIRST, ahead of Deezer, inside the same sequential loop." That
  loop runs on the t2s-CONVERTED terms (`quick-260807-vl1`), which exist because the CN catalogs
  index the Simplified name. Last.fm does not. Probed against production:
  `artist=方大同&track=紅豆` returns the album art; the t2s output `红豆` returns `null`. The planned
  placement would have broken the tier on the exact song the mismatch was reported for.
- **Fix:** The tier runs before the conversion block, on the original `artist`/`title`, sharing the
  same `sawError` accumulator. This is also what parity demands — the client hero queries Last.fm
  with the raw track fields — and a hit now skips the dictionary load entirely.
- **Files modified:** `src/lib/proxy/og-cover.ts`
- **Tests added:** two regression tests pinning it — the Last.fm call must carry `紅豆` and never
  `红豆`, and on a Last.fm miss the tiers below must still receive the converted query.
- **Commit:** `c01288d`

**2. [Rule 1 - Bug] The plan's autoplay-guard regex could never pass**

- **Found during:** Task 3.
- **Issue:** The plan specified `expect(src).not.toMatch(/onMount\(\(\) => \{[\s\S]*?resolveAndPlay/)`.
  The `retry = () => void resolveAndPlay();` binding — which the plan explicitly requires to stay — is
  itself inside the `onMount` body, so the regex matches the correct code. Both guards failed on the
  already-fixed source.
- **Fix:** Extract the `onMount` body and assert `resolveAndPlay` appears exactly once in it (the
  binding), plus the positive assertion that the binding is present.
- **Verified by mutation:** re-adding `void resolveAndPlay();` makes the guard fail; removing it
  again makes it pass. The tripwire is real, not vacuous.
- **Files modified:** both `loader.test.ts` files
- **Commit:** `25b83a4`

**3. [Rule 3 - Blocking] Cache assertions read raw localStorage instead of `getCachedCoverByUid`**

- **Found during:** Task 1, RED.
- **Issue:** The plan said to read the written cache through `getCachedCoverByUid` / `getCachedCover`.
  Both are `vi.fn()`-mocked module-wide in `player.svelte.test.ts`, so they would always return the
  mock value, never the write.
- **Fix:** Assert against the raw `openmusic:cover-cache:v1` record, keyed via the real
  (spread-from-actual) `uidCoverCacheKey` / `coverCacheKey` builders.
- **Files modified:** `src/lib/stores/player.svelte.test.ts`
- **Commit:** `e71bdef`

**4. [Rule 3 - Blocking] `grep -c "swappedCover" → 0` conflicted with the comment-amendment instruction**

- **Found during:** Task 1. The plan asked both to amend comments describing the old behaviour AND
  for the identifier count to reach 0. Reworded the two explanatory comments to describe the old
  field ("a component-local `$state` field") without naming it. Count is now 0 and the decision
  record is intact.

### Assumption Drift (advisory)

**Last.fm script indexing.** Planned assumption: the Last.fm tier could sit inside the existing tier
loop and share its query terms. Actual: Last.fm's index is script-sensitive in the opposite direction
to the CN catalogs — the convert-first pass that fixes CN lookups actively breaks Last.fm ones. This
is recorded because it constrains any FUTURE tier added to this chain: a tier's correct position now
depends on which script its upstream indexes, not only on preference order.

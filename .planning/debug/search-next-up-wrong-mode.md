# Debug Session: search-next-up-wrong-mode

## Symptoms

- **Expected:** With the search playback setting set to "generated", playing a song from the search page should build the next-up queue from songs generated/recommended off the clicked song.
- **Actual:** The next-up list is the other songs from the search page (the search results list) instead of a generated queue.
- **Errors:** (none reported)
- **Timeline:** Per-context up-next sourcing landed in Phase 17 (QUEUE-03). The search-row play handler was never updated to the correct call idiom.
- **Reproduction:** Set search playback mode to "generated" → open search page → play a song → inspect next-up queue.

## Current Focus

- hypothesis: CONFIRMED — search-row play handler called `player.play(t)` without `{ fresh: true }` and set `setListQueue(results, 'search')` AFTER play, so the "generated" regeneration branch never ran and the raw search-results list became up-next.

## Evidence

- timestamp: 2026-06-15 — `src/routes/(app)/search/+page.svelte:571` search-result row handler (before fix):
  `onclick={() => { player.play(t); player.setListQueue(results, 'search'); }}`
  Two faults: (a) no `{ fresh: true }` so `play()` skips the regenerate branch; (b) `setListQueue` ran AFTER `play()` and installed raw `results` as the queue.
- timestamp: 2026-06-15 — `src/lib/stores/player.svelte.ts:1558-1566` fresh-play branch. Regeneration only runs inside `if (opts?.fresh)` and only when `settings.effectiveUpnextMode(this.queueContext) === 'generated'`. Without `fresh`, the else branch just `primeNext()`s — no regenerate.
- timestamp: 2026-06-15 — `src/lib/stores/settings.svelte.ts:460-467` `effectiveUpnextMode('search')` returns the per-context override else global `upnextMode` (default `'generated'`). Resolver is correct; the play path never asked it because `fresh` was absent.
- timestamp: 2026-06-15 — Correct idiom proven elsewhere: `playStub` (`player.svelte.ts:1360-1361`), home (`+page.svelte:609-610`), artist card (`artist/[name]/+page.svelte:150-151`), remix (`TrackMenu.svelte:182-183`) all do `setQueue(list, context)` FIRST then `play(track, { fresh: true })`.
- timestamp: 2026-06-15 — Test `player.svelte.test.ts:1805-1816` confirms intended behavior: `queueContext='search'` + `play(track, { fresh: true })` → `regenerate` runs (mockSimilar called).
- timestamp: 2026-06-15 — Same buggy idiom also present at `artist/[name]/+page.svelte:490` (song row) and `library/+page.svelte:180-181`. Out of scope for this bug but identical latent defect — worth a follow-up.

## Eliminated

- Settings store / `effectiveUpnextMode` resolver — correct; returns 'generated' for the search context.
- `regenerate()` / `buildSimilarQueue` — correct; never invoked because the fresh branch was skipped.
- `setListQueue` anchoring logic — correct; it faithfully installs the list it is given.

## Resolution

- root_cause: The search-result row play handler (`src/routes/(app)/search/+page.svelte:571`) called `player.play(t)` without `{ fresh: true }` and ran `setListQueue(results, 'search')` after play. The per-context "generated" regeneration only fires on a fresh play with the queue context already set, so it was never triggered — up-next fell back to the raw search-results list.
- fix: Reordered to set queue+context first, then fresh-play, matching the established idiom:
  `onclick={() => { player.setListQueue(results, 'search'); player.play(t, { fresh: true }); }}`
- verification: `npx vitest run src/lib/stores/player.svelte.test.ts` → 93/93 pass (incl. the fresh-play→regenerate test at :1805). `npx svelte-check --threshold error` → 0 errors, 0 warnings. With search up-next = "generated", playing a search result now sets `queueContext='search'`, the fresh play resolves `effectiveUpnextMode('search')='generated'`, and `regenerate()` builds up-next from songs similar to the seed.

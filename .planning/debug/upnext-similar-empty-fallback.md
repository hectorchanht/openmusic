# Debug Session: upnext-similar-empty-fallback

## Symptoms

- **Expected:** With up-next mode = "generate by similar songs", playing any track should build the up-next queue from similar-song recommendations for that seed. For a track with no CN similar songs (e.g. YT-only 港耆), the system should still surface similar recs — ideally from YouTube Music (which has related/radio recommendations) — rather than silently switching to a different strategy.
- **Actual:** When a track has no similar songs, the up-next queue silently forms via a different strategy (fallback), ignoring/diverging from the "similar songs" setting, with no indication to the user.
- **Errors:** (none reported)
- **Timeline:** Observed with YT-only tracks. Repro track 港耆 is a Phase-27 YTMusic-only track; CN similar sources (Last.fm track.getSimilar over CN catalog) return nothing for it.
- **Reproduction:** Set up-next mode = "generate by similar songs" → play 摩四老年 《港耆》 [Official Music Video] (YTMusic-only) → inspect what the up-next queue is built from.

## Current Focus

- hypothesis: CONFIRMED. `buildSimilarQueue` (`src/lib/services/similar.ts:173`) is entirely source-agnostic: all three tiers key ONLY on the seed's `artist`/`title` STRINGS (Last.fm `track.getSimilar` → Last.fm/Deezer similar-artists → kuwo-first same-artist `searchAll`). A YT-only seed (摩四老年《港耆》) is absent from Last.fm scrobbles, Deezer's catalog, AND the CN sources, so every tier returns [] and the function hits `report?.('empty'); return []` (similar.ts:245-246). Both callers then SILENTLY fall back to `buildDiversePicks(8, …)` — random pop hits from a hard-coded ARTIST_POOL unrelated to the seed — with the only signal being an Activity-log `upnext.source: diverse` entry. No YTMusic related/radio path is ever consulted (none exists at the source/service layer).

## Evidence

- timestamp: 2026-07-15 — Fresh-play dispatch. `player.svelte.ts:2788` `if (opts?.fresh)` → `player.svelte.ts:2802` `if (settings.effectiveUpnextMode(this.queueContext) === 'generated')` → `player.svelte.ts:2804` `void this.regenerate(resolved).then(() => this.primeNext())`. The resolver `effectiveUpnextMode` (`settings.svelte.ts:471-478`) correctly returns the per-context / global up-next mode ('generated' = "generate by similar songs"). So the setting IS honored up to the point of calling regenerate — the divergence is downstream, inside the empty-similar fallback.

- timestamp: 2026-07-15 — Q1 pipeline (fresh play). `regenerate(seed)` (`player.svelte.ts:3046`) builds an exclude set (head/manual/removed uids) then calls `buildSimilarQueue(seed, exclude, report)` at `player.svelte.ts:3071`. Exhaust-time grow uses the same builder: `ensureAhead()` (`player.svelte.ts:1974`) calls `buildSimilarQueue(current, have, …)` at `player.svelte.ts:2008`. buildSimilarQueue (`similar.ts:173`) has three tiers: (1) PRIMARY `fetchSimilarTracks(track.artist, track.title)` (similar.ts:184) → `apiFetch('/api/lastfm/similar-tracks?artist=…&track=…')` (similar.ts:68) = Last.fm `track.getSimilar`; (2) FALLBACK `getSimilarArtists(track.artist)` (similar.ts:211) → `apiFetch('/api/similar?artist=…')` (similar.ts:43, Last.fm getSimilarArtists) then Deezer `deezerRelatedArtists` (similar.ts:52), each artist resolved single-source via `searchAll(n, 1, prefs)` (similar.ts:214); (3) LAST RESORT `searchAll(track.artist, 1, prefs)` same-artist (similar.ts:234). Terminal miss: `report?.('empty'); return []` (similar.ts:245-246).

- timestamp: 2026-07-15 — Q2 why-empty for a YT-only seed. `grep '\.source\|ytmusic\|videoId'` over `similar.ts` returns ONLY field-construction lines inside `nameStub` (similar.ts:134-138) — the builder NEVER reads the seed's `track.source` or `track.songid` (the YT videoId). Every tier is keyed on the seed's `artist`/`title` STRINGS resolved against Last.fm (tiers 1-2), Deezer (tier 2 fallback), and the CN kuwo-first catalog (tiers 2-3). A Phase-27 YTMusic-only track (摩四老年《港耆》) has no Last.fm scrobble data (tier 1 → `{tracks:[]}` → stubs.length===0, skip at similar.ts:184-185), an obscure artist absent from Last.fm getSimilarArtists AND Deezer related (tier 2 → names.length===0, skip at similar.ts:212), and no CN-catalog entry (tier 3 same-artist searchAll → interleaved empty, lastOut empty at similar.ts:234-241). All three dry → `report?.('empty'); return []`. EXACT failure point: there is no branch anywhere in similar.ts that maps a `track.source === 'ytmusic'` seed (carrying its videoId in `track.songid`) to a YTMusic related/radio lookup — the builder is structurally source-blind.

- timestamp: 2026-07-15 — Q3 fallback + silence. When buildSimilarQueue returns [], the fresh-play path substitutes `tail = await buildDiversePicks(8, exclude); via = 'diverse'` (`player.svelte.ts:3077-3081`) then installs it (`player.svelte.ts:3082`); the exhaust-grow path does the same: `more = await buildDiversePicks(8, have); via = 'diverse'` (`player.svelte.ts:2011-2014`). `buildDiversePicks` (`picks.ts:28`) samples a HARD-CODED `ARTIST_POOL` (`picks.ts:9-12` — 周杰伦, 邓紫棋, Taylor Swift, Ed Sheeran, …) and takes one top track per random artist — completely UNRELATED to the seed. This is SILENT: the ONLY signal is `logAction('upnext.source', { via, count })` (`player.svelte.ts:3085` regenerate / `player.svelte.ts:2018` ensureAhead), which writes to Settings → Activity log ONLY. No toast, no `player.notice`, no UI indication. From the user's view, "generate by similar songs" silently fills up-next with random chart pop → the setting appears ignored. (Historical note: pre-26-09 regenerate had NO fallback and installed the bare [] = dead-end empty up-next; the diverse net at :3077 was added by 26-09/T-26-09-01 to guarantee non-empty — trading an empty list for an unrelated one, still with no user signal.)

- timestamp: 2026-07-15 — Q4 feasibility inventory (factual, no design). The `ytmusic` SourceAdapter (`src/lib/sources/ytmusic.ts:202`) exposes ONLY `search()` (line 213) and `resolve()` (line 235) — no related/radio/watch-next method. API routes under `src/routes/api/ytmusic/` are `search/+server.ts`, `lyrics/+server.ts`, `stream/[videoId]/+server.ts` — no related/next/radio route. HOWEVER the InnerTube plumbing already exists at the proxy layer (`src/lib/proxy/ytmusic.ts`): `NEXT_URL` (`youtubei/v1/next`, line 59 — the exact endpoint that carries YTM's Up-Next/radio/related watch-next queue), `BROWSE_URL` (line 61), generic edge POST helper `innerTubePost()` (line 124), `getVisitorData()` (line 167), `WEB_REMIX_CONTEXT` (line 51). `NEXT_URL` is ALREADY called in production — but ONLY by the lyrics route (`src/routes/api/ytmusic/lyrics/+server.ts:61`), which posts `{context, videoId, isAudioOnly:true}` and consumes ONLY `findLyricsTab(nextJson).browseId`, DISCARDING the watch-next queue/related rows the same response carries. So the transport to the recommendation endpoint is built and proven; what is missing is: (a) a parser that extracts the watch-next queue/related rows into `Track`s (today only `findLyricsTab` reads that response), (b) a client source method or service exposing them (e.g. `ytmusic.related(videoId)` / a `ytmusicRelated()` service), (c) a route or lyrics-route extension that returns the queue, and (d) a branch in `buildSimilarQueue`/`regenerate` that, when `seed.source === 'ytmusic'`, uses `seed.songid` (videoId) against that YTMusic path before/instead of the string-keyed Last.fm tiers. Nuance: `ytmusic` is `autoResolveEligible: false` (ytmusic.ts:210) — search+explicit-pick only — so any YT-derived up-next stubs would need a resolution path consistent with that flag.

## Resolution

- root_cause: The up-next "generate by similar songs" builder is structurally source-blind to the seed's origin. `buildSimilarQueue` (`src/lib/services/similar.ts:173`) resolves recommendations ONLY from the seed's `artist`/`title` STRINGS against Last.fm `track.getSimilar` (similar.ts:184/68), Last.fm+Deezer similar-artists (similar.ts:211/43/52), and the CN kuwo-first catalog (similar.ts:214/234) — it never inspects `track.source`/`track.songid`, and no YTMusic related/radio path exists. A Phase-27 YTMusic-only seed (摩四老年《港耆》) is absent from all three catalogs, so every tier returns [] and the function terminates at `report?.('empty'); return []` (similar.ts:245-246). Both callers — `regenerate()` on fresh play (`player.svelte.ts:3077-3081`) and `ensureAhead()` on exhaust (`player.svelte.ts:2011-2014`) — then SILENTLY substitute `buildDiversePicks(8, …)`, which fills up-next with random hits from a hard-coded ARTIST_POOL (`picks.ts:9-12`) unrelated to the seed. The substitution's only trace is an Activity-log `upnext.source: diverse` entry (`player.svelte.ts:3085` / `:2018`); there is no toast/notice, so the "similar songs" setting appears silently ignored.
- fix: (diagnosis only — no fix applied per goal: find_root_cause_only)
- suggested_fix_direction: Give `buildSimilarQueue` a YTMusic-first branch when `seed.source === 'ytmusic'`, using `seed.songid` (videoId) against a new YTMusic related/watch-next path. The transport already exists (`innerTubePost` → `NEXT_URL`, proxy ytmusic.ts:59/124, already used by the lyrics route); missing pieces are a watch-next-queue parser (→ Track stubs), a service/route to expose it, and the branch in similar.ts/regenerate. Separately, consider surfacing the `via='diverse'` fallback to the user (toast/notice) so the empty-similar case is not silent. Both are out of scope for this diagnose-only session.

# Debug: Background media pill missing + split-second play-then-stop on track-end

## Symptoms

**Expected behavior:**
- Android shows a media notification / top-nav pill while a song plays in the background.
- When a track ends in the background, the next track auto-advances and keeps playing seamlessly with no audible glitch.

**Actual behavior:**
- Two related symptoms while the tab/app is backgrounded (`visibility hidden`):
  1. **No media pill:** Android does not show a "media is playing" pill in the top nav during background playback.
  2. **Split-second play-then-stop on advance:** When the current song ends and advances to the next, a split-second of the next song plays and then stops. Returning to the foreground lets it play normally.
  3. **Variant (no sound leak):** In another observed case, the *next* song was marked dead while the current song was still playing; when the current song ended, the next one showed up but the player stopped entirely (no split-second leak). It started playing again only when switched to foreground.

**Error messages / signals:** No thrown errors. Behavior visible in the action log (Settings → Activity log). See Evidence.

**Timeline:** Observed on Android, background/locked playback. Follows a series of prior background-playback fixes (see Related sessions).

**Reproduction:** Play a queue on Android, background the app / lock screen, let tracks auto-advance to end. Observe missing media pill and the split-second glitch on advance.

## Resolution

root_cause: Symptom 2 (split-second-play-then-stop, and the no-leak variant) — When a track's stream errors while the tab is HIDDEN (region-lock 403 / Android background stream-drop after a brief play; every logged audio.error has hasPlayed:TRUE), the `audio.error` handler's recovery (one in-place reresolveCurrent(), then cross-source runFallback→play) fire-and-forgets `audio.play()`. In a hidden WebView that play() gets no user activation and never re-reaches the `playing` event; reresolveCurrent deliberately does not arm the stall watchdog and the fallback's autoplay-retry is driven off `canplay` (unreliable while hidden). quick-260703-i7e (commit 355303b) had just removed the ONLY foreground resume, so the element sits paused until the user manually acts — the observed "plays a split-second then stops, resumes only on foreground." Symptom 1 (no pill) is, for these stall cases, a downstream consequence: with playback stalled, MediaSession playbackState is left 'paused', so the Android media notification does not show 'playing'. (A residual no-pill during NORMAL never-errored background playback would be an INDEPENDENT native FGS bug — jofr plugin device gate never passed; blocking urlToBitmap ×6 per metadata write — see Evidence 80/82; NOT addressed by this fix.)

fix: [SUPERSEDED — Option A, REVERTED] Restored a narrowly-scoped foreground resume (`pendingRecoveryResume` + `resumeStalledAdvance`). This was reverted at the user's direction (do NOT reintroduce any foreground-resume mechanism — that is what quick-260703-i7e deliberately removed).

fix (ACTIVE — Option B: treat a background stream-error as a SKIP, not a resume): In the `audio.error` handler (player.svelte.ts ~line 1397-1422), after the single in-place `reresolveCurrent()` fails for a track that has ALREADY produced audio (`hasPlayedSinceSrc`) and the `reresolve.cap` fall-through is reached, a NEW guard checks `document.hidden`. If the tab is backgrounded, it logs `bg-error-skip` and calls `next()` — the EXISTING advance/skip path (advanceTo → play, which bumps playGen and supersedes the errored src, reusing the never-stop dead-track skip semantics) — INSTEAD of handing off to `runFallback`. `runFallback`'s cross-source `play(swap)` is a fire-and-forget `audio.play()` that never re-reaches `playing` in a hidden WebView, so it left the element paused (the observed "split-second then stop"). The action log confirms subsequent tracks play cleanly in the background, so a forward skip keeps playback alive. Scope: `document.hidden` + `hasPlayedSinceSrc` — a FOREGROUND error still gets the richer cross-source `runFallback`. An external audio-focus loss (voice note) fires `pause`, NOT `audio.error`, so it never enters this branch → no skip, no resume → i7e's "do not fight the OS" mandate is intact. Symptom 1 (pill) is handled downstream: the forward-advance `play()` sets MediaSession `playbackState='playing'` (running artifact = Web PWA, web MediaSession only — no native FGS path touched), so the pill persists on the surviving track.

<objective>
Replace the single unofficial-Google provider inside `/api/translate` with an ordered cascade Azure Translator → DeepL Free → unofficial-Google that advances on transport error / non-2xx / rate-limit / echo (D-05). Keys are optional and edge-only (D-06). The chunk/sentinel/echo-mode/per-line-fallback machinery and the `{ translated, flags }` contract are preserved unchanged.

Purpose: the current single free-Google upstream rate-limits and silently echoes originals under load, which is the root cause of intermittent zh-Hant failures. A cascade keeps translation working when one provider is down.
Output: cascade-aware `+server.ts`, optional provider keys typed in `Env`, `.dev.vars` placeholders, and a server-side test suite.
</objective>

    Generalize the single `gtranslate(text, to)` into an ordered cascade WITHOUT changing the `GResult { text, segments }` return shape — so `translateChunk`, `perLine`, the sentinel split, and the echo-mode guard all keep working unchanged. Define three provider functions each `(text: string, appTo: string, env: Env | undefined) => Promise<GResult | null>`:

    - `azureTranslate` — POST to `https://api.cognitive.microsofttranslator.com/translate?api-version=3.0&to=<azureCode>` with headers `Ocp-Apim-Subscription-Key: env.AZURE_TRANSLATOR_KEY` and `Ocp-Apim-Subscription-Region: env.AZURE_TRANSLATOR_REGION`. Returns null immediately if `env?.AZURE_TRANSLATOR_KEY` is absent (skip tier). Map the app target to Azure's BCP-47 code (`zh-Hant`→`zh-Hant`, `zh-Hans`→`zh-Hans`, others pass through); return null if the target is unsupported so the cascade advances. Set `segments` to the number of translated segments returned so the existing echo-mode guard still applies.
    - `deeplTranslate` — POST to `https://api-free.deepl.com/v2/translate` with header `Authorization: DeepL-Auth-Key <env.DEEPL_KEY>`, `target_lang` mapped (`zh-Hant`→`ZH-HANT`, `zh-Hans`→`ZH-HANS`, en→`EN`, ja→`JA`, etc.); return null if `env?.DEEPL_KEY` is absent OR the target is unsupported by DeepL (advance).
    - `googleTranslate` — the CURRENT `gtranslate` body verbatim (keyless, unofficial-Google), mapping via the existing `LANG_MAP` (`zh-Hant`→`zh-TW`). Last resort; always attempted.

    Introduce a single `cascade(text, appTo, env): Promise<GResult | null>` that tries providers in order [azure, deepl, google] and returns the FIRST result that is a genuine translation. Treat a provider as "failed" (advance to next) on: it returned null (transport error / non-2xx / absent key / unsupported lang), OR the result is echo-mode (a multi-segment source that came back as a single segment — reuse the existing `segments <= 1` heuristic), OR the returned text equals the input (echo). If every provider fails, return null so the existing per-line fallback still runs.

    Rewire the two current `gtranslate(...)` call sites (single-line POST path + inside `translateChunk`/`perLine`) to call `cascade(..., env)` instead. Thread `env` from the POST handler down through `translateChunk` / `perLine` (add an `env` parameter). Keep CHUNK_SIZE, PERLINE_CONCURRENCY, the sentinel scheme, and `reply()` untouched. RAW `fetch` remains correct (edge-side absolute upstream URLs — NOT `apiFetch`); keep each provider on `AbortSignal.timeout(TIMEOUT_MS)`.

    Keep the incoming `to` as the APP code (e.g. `'zh-Hant'`) down through the cascade so each provider maps it itself; only `googleTranslate` uses `LANG_MAP`. Preserve the top-level validation that rejects an unknown `to` (return the originals with all-false flags) — but base "supported" on the union of providers (i.e. anything in `LANG_MAP` is at least Google-supported).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → /api/translate | Untrusted `{ lines, to }` POST body crosses into the edge handler |
| edge → Azure/DeepL/Google | Server-side fetch carrying provider secrets in headers |
| platform.env → handler | Cloudflare-injected secrets; must never reach the client |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-25c-01 | Information Disclosure | AZURE_TRANSLATOR_KEY / DEEPL_KEY | mitigate | Keys read only from `platform?.env` (edge), injected into upstream headers, never in `reply()` body or client bundle (parity with JOOX_TOKEN); test 5 asserts absence in response |
| T-25c-02 | Tampering / Spoofing | untrusted `lines` / `to` input | mitigate | Preserve existing input coercion (`String(x)`) + `to` validation against the supported map before any upstream call |
| T-25c-03 | Denial of Service | provider fan-out | mitigate | Cascade is SEQUENTIAL per chunk (advance-on-failure, not parallel across providers); keep CHUNK_SIZE + PERLINE_CONCURRENCY caps + per-request AbortSignal.timeout |
| T-25c-04 | Denial of Service | provider quota exhaustion | accept | Free-tier quotas (Azure 2M/mo, DeepL 500k/mo); on 429/quota the cascade advances to keyless Google — degrades, never blocks |
</threat_model>

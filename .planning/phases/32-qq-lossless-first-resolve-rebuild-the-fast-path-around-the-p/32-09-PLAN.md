<objective>
Restore a short-TTL `url` payload beside the permanent `song_mid` in the edge resolve entry (32-D-20),
so a warm play in the PoP is 0.44s-to-playable again (the Phase-31 measured path) instead of always
paying the 2.0–3.8s tang detail RTT that 32-04's url-less entry left as the floor.

32-04 removed `url` on the reasoning "it was the only reason this entry had to expire" — true under a
single-TTL entry, obsoleted minutes later by D-10a's per-payload TTL split. This plan reconciles the
two: `songid` stays permanent, `url` lives beside it with its own short lifetime, and the failure path
stays the load-bearing half (31-D-08/D-09/D-11, re-accepted by D-20 for the 0.44s).

**Primary acceptance criterion of this whole plan: the POISONED hit, not the fast hit.** A 403/dead/
expired cached url must fall through to the mid path, refill, and play — no user-visible error, no
user-visible latency spike beyond an ordinary miss. Every task's headline test is that fall-through.

Purpose: D-20 — the last latency lever the phase decision record names.
Output: v3 entry shape, edge-side url refill, client url→songid→cold-walk read order, poisoned-hit
test coverage at three layers (cache module, route, catalog seam).
</objective>

## Design decisions (read before Task 1 — these ARE the plan)

1. **url freshness lives IN the payload, not in a second Cache-Control.** The Cache API stores ONE
   Response per key with ONE max-age, so "mixed lifetime" is implemented as: the entry keeps 32-04's
   payload-driven TTL branch byte-for-byte (`entry.songid` present → `public, max-age=31536000,
   immutable`; else `public, max-age=900`), and the url's short lifetime is a `urlExp` epoch-ms field
   the EDGE checks at read time. This is exactly how D-10a's machinery makes a mixed-lifetime entry
   a solved problem — `writeResolveEntry`'s TTL logic does not change at all.
2. **`RESOLVE_URL_TTL_S = 900` — a dedicated constant, same value as `RESOLVE_TTL_S`.** 900s is the
   value Phase 31 shipped and measured working (0.44s hits, url deaths inside the window handled by
   the bust, not the TTL). It gets its own name because `RESOLVE_TTL_S` now means "negative-entry
   TTL" and the two concepts must stay independently tunable. `urlExp = Date.now() +
   RESOLVE_URL_TTL_S * 1000` is baked at write (one comparison at read; re-tuning applies to new
   writes only, which is fine for a 15-minute window).
3. **The refill is EDGE-ONLY, refresh-on-read.** There is still deliberately NO client write path
   (T-31-03-03 anti-poisoning: the entry is shared text-keyed PoP data). On a GET hit whose `songid`
   is present but whose url is absent or stale, the route schedules `waitUntil(resolveUrlOnEdge(mid))`
   — ONE tang detail subrequest, mid already in hand — and rewrites the entry with a fresh url. This
   ONE mechanism covers initial absence (the search fill never fetches a url), 900s expiry, and
   post-bust refill (bust → miss → search fill → next read triggers the url fill). Consequence kept
   on purpose: `resolveOnEdge` stays exactly ONE subrequest — 32-04's fill win survives verbatim.
4. **The GET view nulls a stale url.** The client contract is "url present ⇒ fresh". Freshness has
   ONE authority (the edge, same clock that wrote `urlExp`); the client never reads `urlExp`.
5. **The url is filled at ONE canonical tier — lossless — and the entry records it (`urlQuality`).**
   A shared single url cannot serve two tiers; lossless is the phase's namesake tier and D-01's
   primary. The client adopts the url only when `entry.urlQuality === effectiveQuality(quality ??
   settings.defaultQuality)`. A '320'/'128' caller therefore ignores the url and takes the mid path —
   exactly the post-32-04 behavior, no regression, and never a wrong-tier play (a cellular 'auto'
   user must not be handed a 50MB FLAC url).
6. **The edge gets a small rung mirror, not an import of `sources/qq.ts`.** `sources/qq.ts` imports
   the settings runes store and the client apiFetch governor — both browser-side; `resolve-edge.ts`'s
   standing rule forbids referencing the client fetch seam, and its header already records "the cost
   of that guarantee is this small server-side mirror of the qq search contract". The detail mirror
   is the same accepted cost: a fixed lossless walk `sq → pq → hq → standard → fq`, NEVER
   `song_play_url_accom` (32-D-18: 伴奏/.ogg) and never the untyped bare `song_play_url` fallback,
   plus the `http:`→`https:` upgrade (32-D-05). Comment must cross-ref `sources/qq.ts pickBestPlayUrl`
   as the client authority and name both decision refs so drift is caught in review.
7. **Client-side reported-dead strip closes the bust race.** `reportDeadUrl` fires the POST bust, but
   the bust is async and PoP-local — a re-resolve in the same second can read the not-yet-busted
   entry and re-adopt the exact dead url. Fix at the ONE read seam: `readOrThrow` nulls `entry.url`
   when the module's `reported` set already contains it. This is the line that makes "a poisoned hit
   is indistinguishable from a miss" true deterministically, not just eventually.
8. **SKIP-WHEN-MID-HELD narrows (the subtlest change, per D-20's mandate to re-examine it).** 32-04
   skipped the cache read whenever the track held a qq mid, because the entry could only hand back an
   identifier the caller already had. Under D-20 a mid-holder CAN gain a url hit (zero tang RTT), so
   the gate becomes: read the cache when the lyric-re-resolve bypass does not apply AND
   (`!hasQqMid` OR the effective tier is `'lossless'`). A lossless mid-holder — the phase's primary
   persona — pays ≤400ms bounded for a chance at saving the 2.0–3.8s RTT; a '320'/'128' mid-holder
   keeps 32-04's skip untouched (the url is lossless-only by construction, so they can gain nothing).
   The `resolve.midless` log keeps its exact 32-04 condition (`!hasQqMid` on a cold resolve).
9. **`RESOLVE_CACHE_VERSION` '2' → '3'.** Adding `url`/`urlExp`/`urlQuality` IS a shape change; a
   shape change is a KEY change, never an in-place migration (`cache.delete` is PoP-local, no global
   purge exists). Non-negotiable.
10. **The `lrcUnresolved` writer returns to catalog.ts — deliberately.** 32-04's SUMMARY records
    "zero writes of the flag remain in catalog.ts" as an outcome; the url-hit branch reinstates one
    writer (a cached url carries no lyrics — the 31 flag's original reason). Record this reversal in
    a 32-D-20 comment at the write site so a verifier reading 32-04's SUMMARY doesn't file it as a
    regression.

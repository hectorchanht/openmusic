The full phase: a `/api/resolve` edge cache with a delete-only bust, a client cache-first read that falls through invisibly on any failure, corrupt-download self-repair, a more forgiving strike policy with cross-source retry, skip toasts, and two-trigger pre-warm.   <how-to-verify>
**A. Real Cache API hit/miss/delete (D-07, D-09).** `vite dev` has no Cache API — `edgeCache()` returns `null` there and every cache path is inert, so a `pnpm dev` check will always show a miss. Use the workerd runtime instead.

1. Run `pnpm preview` (wrangler pages dev, Miniflare 3 — it simulates the Cache API in memory).
2. `curl -s -w '\n%{time_total}\n' 'http://localhost:4173/api/resolve?a=Olivia%20Dean&t=Man%20I%20Need'` — expect `{"hit":false}` returned fast.
3. Wait ~5s for the `waitUntil` background fill, then repeat the identical curl — expect `{"hit":true,...}` with a populated `entry.url`.
4. `curl -s -X POST -H 'content-type: application/json' -d '{"a":"Olivia Dean","t":"Man I Need"}' 'http://localhost:4173/api/resolve'` — expect `{"busted":true}`.
5. Repeat step 2's curl — expect `{"hit":false}` again (the entry is gone).

Record all five outputs. If step 3 never turns into a hit, that is a real finding — do not paper over it.

**B. Measured click-to-play latency (D-01..D-05) — the phase's whole point.** No timing harness exists in the repo and `apiFetch` is mocked in every unit test, so this is measurement, not assertion.
1. Probe the dev server port first — it is 4321 via `.claude/launch.json` or 5173 via a bare `pnpm dev`. Do not assume.
2. In DevTools, install the spike-003 fetch wrap: override `window.fetch` to push each URL into `window.__net`, and reset `window.__net = []` at the click boundary.
3. Search a song, wait for results to render (this fires the pre-warm), then tap the top result. Count and categorize `window.__net`.
4. Cross-check with Settings → Activity log timestamps: `play` → `resolve.ok` → `playing`.
5. Repeat for a track pre-warmed via long-press (menu open) and for a cold track further down the list.
Record the call counts and the play→playing deltas for all three cases.

Note the sandbox constraint: only the netease and qq Meting proxies are blocked here; kuwo and Deezer are reachable, so the kuwo-first resolve path IS live-verifiable.

**C. Device-only behaviours (D-12, D-15, D-16).** Background playback, lock screen and autoplay policy are device-only reproducible and the Activity log is the diagnostic channel. If a device is available, install the APK and confirm: a track still auto-advances with the screen locked, and no `recovery.halt` fires on a normal queue. If no device is available, say so explicitly in the summary rather than marking it passed.

**D. Corrupt-download self-repair (D-12/D-14), if convenient.** Download a song, corrupt or truncate its IndexedDB blob via DevTools → Application → IndexedDB (`openmusic-blobs` / `tracks`), then play it. Expect exactly one "Download was corrupted · streaming instead" toast, uninterrupted playback, and a `blob.corrupt` entry in the Activity log.
  </how-to-verify>

<objective>
Make the up-next "generate by similar songs" builder source-aware: when the seed is a YTMusic track
(`seed.source === 'ytmusic'` with a `seed.songid` videoId), `buildSimilarQueue` fetches the related radio
queue (plan 28-01's `/api/ytmusic/related`) via a new `ytmusicRelated(videoId)` client service that maps
rows to REAL `ytmusic` Track stubs, and reports `via='ytmusic-related'` — BEFORE/INSTEAD OF the string-keyed
Last.fm tiers (which are structurally dry for a YT-only seed). CN / non-YT seeds keep the existing 3-tier
behavior byte-for-byte.

Purpose: Requirement UPNEXT-YT-02 (source-aware branch keyed on seed.source + seed.songid; honor
`autoResolveEligible:false`). Fixes the diagnosed root cause (`buildSimilarQueue` is source-blind →
YT-only 港耆 returns `[]`).
Output: `src/lib/services/ytmusic-related.ts`; the YT branch in `buildSimilarQueue`; a widened report/via
union; branch + mapper tests.
</objective>

CRITICAL constraints:
- Build YT related stubs as REAL ytmusic stubs, NOT `resolveByName` name-stubs. A name-stub routes through
  `resolveNameStub`, which EXCLUDES ytmusic and tries kuwo→qq→… by name — the 港耆 radio rows are YT-only HK
  indie absent from CN catalogs, so name-stubs would produce a DEAD up-next. Real ytmusic stubs resolve through
  the adapter's own `resolve()` → `/api/ytmusic/stream/{videoId}`. `autoResolveEligible:false` bars only the
  REVERSE direction (a non-ytmusic track failing over TO ytmusic; a name-stub auto-resolving to ytmusic) — it
  does NOT block a ytmusic-origin track resolving through its own adapter (28-RESEARCH §Q4).
- The YT branch fires ONLY for `seed.source==='ytmusic' && seed.songid`. Any other seed runs the existing tiers
  unchanged → ZERO added calls, ZERO CN regression (28-RESEARCH §Q6).
- On an EMPTY YT related result, report `'empty'` and return `[]` — do NOT fall through to the Last.fm tiers
  (they key on artist/title strings and are dry for a YT-only seed; the player's fallback net then fires).
- Never-throw at the service boundary (UPNEXT-YT-03).

<objective>
Build the YTMusic related/watch-next edge source: a pure parser (`parseWatchNextQueue`) in
`$lib/proxy/ytmusic.ts` plus a new `GET /api/ytmusic/related?videoId=` route that POSTs the InnerTube
`NEXT_URL` with the RADIO body (`playlistId: 'RDAMVM' + videoId`) and returns a trimmed
`{ tracks: [...] }`. This is the missing transport that lets a YTMusic-only seed (repro `dUlAfTZkjpE`
/ 港耆) surface genuinely related songs — the same `NEXT_URL` response the lyrics route already fetches
but discards.

Purpose: Requirement UPNEXT-YT-01 (parse watch-next queue → rows; route reusing existing transport).
Downstream plan 28-02 consumes this route's `{ tracks }` shape to build up-next stubs.
Output: `parseWatchNextQueue` + `YtRelatedRow` + `RADIO_PLAYLIST_PREFIX` in `$lib/proxy/ytmusic.ts`; the
`related/+server.ts` route; a captured fixture; parser + route unit tests.
</objective>

CRITICAL project constraints (from CLAUDE.md + MEMORY):
- SvelteKit `+server.ts` may export ONLY HTTP verbs. A top-level non-verb `export function` in a route
  throws `Invalid export` at REQUEST time — a 500 that unit tests miss (they import the module directly)
  and only E2E catches. This exact bug hit Phase 27 (quick-270715, commit 29c1c7d). Therefore the parser
  and all interfaces MUST live in `$lib/proxy/ytmusic.ts`; the route file exports only `GET` and `OPTIONS`.
- Never-throw at the edge: the route degrades to `{ tracks: [] }` on any upstream/parse failure — never
  a stack trace, never a 500 (UPNEXT-YT-03).
- Untrusted upstream JSON: optional-chain every renderer path, zero `as any` in production source, tabs
  indentation, single quotes.
